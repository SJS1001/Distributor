# Fixed native failed-refund application and exact recovery

The internal [Integration operation](../src/server/integration-offline-failed-refund.ts) applies one captured failed Stripe refund comparison through actual Billing, Integration and Platform owners in the caller's existing synchronous native writer. [Native tests](../tests/integration-offline-failed-refund.test.ts) cover CA/CAD, CA/USD and US/USD synthetic stores. This supplies native consistency engineering for accepted D-010/D-024/D-039. It does not qualify external evidence or pass a product gate.

## Fixed operation and boundaries

The task is `integration.offline-failed-refund`, version 1, with the finance actor's organization, no sites, expected revision zero and no prior claim. The operation accepts only a comparison captured by the actual fixed comparator; copied, proxied, revoked and accessor inputs fail before callbacks. It detaches actor ID and organization descriptors, reloads current native IAM, requires finance permission, refuses buyer/password-change principals and checks the actual raw recovery hold.

The existing native phase reader checks the actual opened database, file identity, generation, candidate hash, session revision and complete no-release history. The existing native refund join checks actual Integration unknown-effect/poll/history and Billing invoice/payment/credit/refund histories inside the same writer. Envelope payload and expected-state hashes bind the exact captured comparison and native join. The failed tuple uses the actual Stripe PaymentIntent external reference; the local Billing payment-row ID is not a provider identifier.

Before mutation, complete fixed Integration effect, inbox, callback, poll, lease, provenance, checkout and accounting sets are counted and checked for native scalar types, safe integers, NULs and UTF-8 byte limits. The first profile refuses checkout/accounting descendants, callbacks/inbox/leases and competing provenance instead of importing them. Bounds are 256 rows per fixed set, 512 aggregate rows, 64 KiB fields, 128 KiB rows and 2 MiB aggregate text. Conservative JSON lexical limits precede SQLite JSON validation and parsing. The receipt record reserves space before the first write.

Billing owns the unknown-to-rejected transition, original applied observation and notice. Integration conditionally stores the canonical failed result and provider reference, then inserts immutable provenance. Platform records the exact task binding and result hash in its native session history. All changes share one transaction. The caller must propagate every error through that outer transaction. A real prior Platform receipt with the same task/request identity causes a late native conflict after provenance insertion; the test verifies complete financial, Integration and Platform rollback. Unsupported added schema also refuses before mutation.

No Application route, CLI, schema, provider transport or enabled commit guard is added. The default restore commit guard remains disabled. Independently qualified source/candidate fencing, current external trust/revocation/clock and authority, provider truth, residency and a fence held through actual COMMIT remain necessary before operational composition. A captured synthetic comparison alone cannot grant them.

## Exact retained recovery

Recovery uses the actual current native IAM and raw hold, complete fixed-set preflight and retained Platform receipt reader. It checks same-read UTF-8 byte witnesses, immutable provenance hash, exact envelope/binding, original native join hash, fixed failed tuple, current Integration effect and original poll history. Billing verifies the original applied observation and notice receipt, allowing later ignored observations without replacing that receipt. The result is frozen and read-only; `total_changes()` remains unchanged. Reopening the same database recovers the identical receipt. Ordinary notice acknowledgment remains excluded during the open offline phase.

Recovery refuses changed effect/result/reference/state, copied poll claims, changed permissions, malformed/oversized/deep text, unsafe native integers and unexpected checkout/accounting descendants. Provenance UPDATE, DELETE and implicit replacement refuse through actual append-only storage rules. These checks establish retained native consistency, not current provider truth, retry, release or independent external authorization.
