# Local billing documents and aging

Date: 2026-09-30, America/Toronto. Implementation checkpoint for D-022–D-025; no task or product gate is verified. Use [implementation status](IMPLEMENTATION.md), [financial checkpoints](CHECKPOINTS.md), [local receipt](evidence/LOCAL-BILLING-DOCUMENTS-2026-09-30.md) and [dependency notices](THIRD-PARTY-NOTICES.md).

## Issuance and original facts

Billing owns party profiles, immutable document facts, stored PDF renditions and prepared download receipts. Finance/administrator can update issuer/customer billing names, addresses, tax registrations and customer terms with a reason and expected profile version. Empty addresses/tax registrations and unknown terms remain explicit. Names and registrations are recorded evidence, not verification of a legal identity or tax policy. Customer terms accept 0–365 calendar days; issuer profiles cannot set terms.

New native invoices capture both identities, their versions, exact original quantities/unit net/unit tax, currency, issued date, customer terms and derived due date inside the invoice transaction. No retrospective profile change rewrites those facts. Issued credit notes inherit original invoice identities and carry original invoice number, credited quantities and reason/reference. Current payments, credits or refunds never alter original PDF amounts. Each facts record must reconcile original line net/tax totals to the original document total; its hash is verified on access.

Earlier native invoices cannot recover missing historical identities/terms. Their first download records current billing identities explicitly as reconstruction, leaves due dates unknown and never applies current terms retrospectively. Imported opening invoices retain original due date, gross/credited/paid/refunded/outstanding amounts and source/cutoff provenance. Their PDF states that it is a reconstructed opening invoice, not the original source PDF, and that original identities are unavailable. Imported historical credited amounts have no invented original credit-note identity. See [unpaid-document imports](IMPORTS.md).

## Authorized downloads

The Billing screen offers Download invoice PDF and Download credit PDF. The authenticated POST route is `/api/billing/documents/:kind/:documentId/pdf`, with an empty JSON object, current same-origin session/CSRF and an idempotency key. Finance, commercial, warranty and support readers (plus administrators) are organization-scoped; buyers are account-scoped. Current principal and document authority are checked before cached results. After asynchronous rendering the session is re-read; expired sessions, deactivated users or changed account/role cannot receive cached bytes.

Facts preparation commits first. Rendering occurs outside a database transaction. The final transaction chooses one stored rendition, verifies fact/byte hashes and atomically records a `prepared` receipt plus command/audit evidence. A late receipt write failure rolls back bytes and request evidence; immutable prepared facts remain for retry. Simultaneous requests use the first committed rendition. A repeated key reuses one receipt/identical bytes; a new key records another authorized request for the same bytes. Stored renderer/facts/content hashes and bytes persist across restart; corruption fails before delivery. The browser retains its request key until it receives and verifies the PDF MIME type and SHA-256 header, so a lost committed response retries the original receipt.

Receipts record requested actor/time, account/document, safe ASCII filename, exact byte count/hash and state. They establish prepared bytes, not that a file was saved, read, emailed, delivered or accepted. History shows the latest 200 authorized requests; audit/command evidence remains persisted. PDF responses use private no-store headers. PDFs carry original values, explicit missing details, page numbers, facts hash and reconstructed-document qualifications. Static Noto Sans supports tested English/French text, wrapping and pagination; unsupported glyphs/control characters fail without a prepared download. Additional scripts/font coverage, large rendering workloads and signed file archival remain unqualified.

## Current aging and export

Account aging reads current native ledger balances, using UTC calendar days from immutable native due dates or original imported due dates. It shows not due, 1–30, 31–60, 61–90, over 90 and unknown due. Unknown legacy/unspecified due dates are not assigned an invented overdue age. Positive debt and negative credit balances remain separate; signed net, order holds and pending/unknown refunds appear independently. Pending refunds do not represent settled cash. This is a current observation with a timestamp, not an arbitrary historical statement or currency conversion.

Finance/administrator can export `/api/billing/aging.csv`. Monetary fields are integer cents with account currency and observation timestamp. String cells quote embedded characters and prefix spreadsheet formula/control-leading values. A platform-owned export command/audit preserves actor, observation, account IDs and CSV hash with state `prepared`; it does not claim delivery. Buyers see only their own aging/download history and cannot edit profiles or export organizational aging.

## Native customer inbox — local checkpoint 2026-10-01

Finance/administrator uses **Review and publish invoice/credit** on the Billing screen. The browser verifies and downloads the existing immutable PDF, then asks the operator to review the exact document and customer and supply a reason before **Publish to customer inbox**. The server requires that same operator's original prepared-download receipt, verifies the persisted facts/bytes and records one active publication per original document. It does not assert that a human actually opened or approved the PDF.

Only a current buyer for that customer account can download a publication from the inbox. Downloading records a `prepared` request and does not record receipt confirmation. After verifying the PDF MIME type and SHA-256, the browser displays **Confirm document receipt**; cancellation leaves no acknowledgment. **Confirm receipt** explicitly records the buyer, account, publication, exact content hash, their own prepared request, time and versioned statement: receipt does not imply payment or agreement with its contents. Staff cannot confirm for a buyer. Repeated requests deduplicate personal acknowledgment; each buyer confirms separately.

Finance can withdraw an available publication with its current revision and a reason. The original invoice/credit, downloaded copies, prepared requests and existing confirmations remain. Current state and grants are checked before cached buyer downloads/confirmations. Republishing creates a new publication ID for the original bytes and requires a new publication-specific buyer download/confirmation. A lost publish response retried after withdrawal reports the withdrawn state. No withdrawal changes a financial balance, stock or shipment.

Inbox history returns at most 200 publications, with up to 200 requests/confirmations per publication; buyers see only their account and their own personal request/confirmation evidence, while authorized staff see organization evidence. Production pagination, retention and operational scale remain pending. The [local inbox receipt](evidence/LOCAL-BILLING-INBOX-2026-10-01.md) covers domain/HTTP/process checks and existing browser regression; the new publication/confirmation UI journey still needs dedicated browser and human acceptance evidence.
