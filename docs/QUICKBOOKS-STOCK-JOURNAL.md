# QuickBooks stock journal protocol candidate

This is disabled sandbox protocol groundwork for D-034/D-036/D-039. It has no application route, native effect queue, worker or startup binding. It does not deliver a stock-cost packet, establish ledger posting or verify a product gate. Do not attach it to the existing buyer-scoped provider runtime: a whole-organization stock journal requires an organization-scoped authority and residency model.

The candidate accepts the exact downloaded original [stock-cost file](ACCOUNTING-COSTS.md) or approved [mapping correction](ACCOUNTING-CORRECTIONS.md), an explicit QuickBooks realm/account mapping, one approved date and a closed-through date. Integrity, review metadata, organization, regional currency, outcome, positive cent amounts and balanced daily journals are checked. It preserves individual movement/account postings. Original files with multiple dates become separate intents; the adapter never moves them into a different period. Distinct source accounts cannot collapse into one receiver account. Limits are local refusal controls: 2 MB source, 4 MB effect payload, 20,000 source lines and 1,000 selected lines/accounts; actual provider limits still need qualification.

Each request uses a stable effect identity, a 21-character document number and a full source/intent marker. Only journal lines and those markers leave the adapter; the original artifact is not sent wholesale. The payload still contains the source artifact and must receive the native store's normal protection. Company financial locale/home currency and active eligible receiver accounts are checked. Accounts requiring customer/vendor entities or cash semantics, FX, tax lines, adjustments and unexpected dimensions are refused. Country/locale does not prove provider processing residency.

Intuit documents balanced debit/credit distributions, account references, journal dates, document identifiers and query/create operations. Canadian tax mode is explicit. Request fields and conservative receiver validation follow the [JournalEntry reference](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/journalentry). Home currency follows the documented [Preferences reference used by Vendor](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/vendor); financial locale is described by the [CompanyInfo Country property](https://static.developer.intuit.com/sdkdocs/qbv3doc/ippdotnetdevkitv3/html/51eded02-099e-8ac1-be14-2faac589b24d.htm). Reviewed on 2026-10-03 through official indexed documentation; the interactive reference did not render its full body in the read-only browser. Older SDK descriptions are not evidence of current sandbox behavior.

## Send and reconciliation boundary

Transport is hard-coded to the QuickBooks sandbox and disabled by default. An injected native authority guard is mandatory before credential access and after credential refresh, on every read and immediately before a write. Execute requires a per-call native write fence argument before any IO is attempted; immediately before POST that fence must complete synchronously and return no value. An asynchronous fence refuses posting. The effect is copied and frozen before the first asynchronous boundary; caller mutation cannot change the selected source, realm or request identity. Redirects are refused and requests time out after 20 seconds. There is no internal retry.

Send performs an exact document-number lookup before its single POST. One fully matching existing journal returns its observation without another write. Multiple, partial, altered or conflicting results refuse. Receiver checks compare full source marker, date, currency and every posting, including line identity, debit/credit direction, account and exact cent amount. Equivalent line ordering is permitted; duplicate or missing lines are refused. System journal totals, if returned, must be zero; native debit and credit totals come from the validated lines.

Lookup performs GET only. An absent record returns no confirmed result. It is not cancellation or final non-posting evidence and must never enable automatic resending. A lost or invalid create reply remains uncertain; only a matching observed record can establish this adapter's result. That result is a protocol observation, not a durable native receipt or an independent finance reconciliation.

## Native engineering still required

The guard is an explicit contract, not an implemented authorization service. Before wiring this adapter, build an organization-owned integration operation with:

- Current finance/operator and worker authority, named QuickBooks organization residency choice, current disclosure acceptance/withdrawal and an exact configured realm. Buyer consent must not be borrowed for organization records.
- Current provider/recovery hold, approved source hash, posting owner and period policy, reviewed immutable receiver account mapping, permanent per-date/per-leg effect/reference reservations and exclusive durable lease ownership.
- Reversal-before-replacement delivery, append-only provider observations bound to native correction/retry histories, unknown-outcome fencing, stale lease recovery and fresh separately approved attempts after independently established cancellation/non-posting.
- Credential refresh scoped to the organization's operation and consent, transactional queue/history/API controls and interruption/restart/concurrency fault checks. Native effect payloads cannot be caller-authored source approval.

The generic buyer-effect controller cannot satisfy these checks. Do not use a no-op guard or create a synthetic customer account to bypass that boundary. Actual CA/US sandboxes, current supported journal/tax/account fields and limits, vendor processing locations/terms, finance mappings/periods and independent outcomes require separate qualification. No live provider IO, account, workflow or runner job was created for this candidate. The [local receipt](evidence/LOCAL-STOCK-JOURNAL-2026-10-03.md) records synthetic tests and exact inputs.
