## Technical foundation

New TypeScript modular application, Node 24.16, native SQLite with WAL and FULL durability, Fastify HTTP boundary and React staff/buyer interface. No OPUS or UB code, database, credentials or runtime dependencies. Each module owns prefixed tables; the database authorizer rejects cross-owner SQL reads/writes. Cross-module business changes use synchronous `BEGIN IMMEDIATE` transactions through owning operations. External requests happen after intent commits.

SQLite is an initial single-node implementation choice, not a demonstrated production capacity claim. Recovery, load targets, deployment region, independent review and operator qualification remain required. Current schema creation is a foundation, not a tested upgrade migration system.

## Owner targets and residency

US and Canada; USD/CAD with no implicit exchange or cross-currency allocations. Each runtime has one declared residency region and each organization belongs to that region. Canadian and US stores/backups/logs must be deployed separately within their approved region; a code flag alone cannot prove infrastructure residency. Synthetic local fixtures do not establish production hosting location.

Stripe and QuickBooks are selected targets. QuickBooks Online is the proposed API edition; confirm the actual edition and company mappings. The owner instructed that residency be a customer choice. Accounts default to strict regional residency. Customers may explicitly accept named processor exceptions; the choice is versioned/audited and rechecked before outbound processing. A different regional storage choice requires an approved migration rather than a flag that misrepresents storage location. Provider egress stays disabled until endpoint credentials and runtime provider access are configured. [Stripe's DPA](https://stripe.com/en-ca/legal/dpa) section 6 states that data is transferred to the US and may be processed globally; Canadian-only end-to-end residency cannot be claimed for Stripe without a separately qualified arrangement. QuickBooks provider storage/processing and backup locations also need vendor evidence. Local residency is distinct from those processor exceptions.

The [provider/device plan and runbook](PROVIDERS.md) defines proposed UPS, FedEx, USPS, Canada Post, Purolator, DHL Express and Zebra/Honeywell/Datalogic/Brother qualification candidates. No specific service/device is qualified. Manual collection/tracking and typed or keyboard-wedge serial input exist locally. Feature-detected native browser camera input and durable receipt drafts exist locally; reviewed identity-only stock QR PDF downloads exist locally; actual camera/scanner/printer models, physical printed readability and individual carrier protocols require qualification against official APIs and real equipment. No API stub counts as provider certification.

## Local operation

Requires Node 24.16.x and npm. From the repository:

```sh
npm ci
npm run build
npm run demo
npm start
```

The explicit demo command initializes an empty database with synthetic equipment, two warehouses and a customer. It prints generated local demo credentials; keep these local. Open http://127.0.0.1:3000. A populated database rejects bootstrap rather than resetting existing records. For an empty installation without fixtures, use `npm run bootstrap` with administrator credentials supplied through stdin or environment. See `.env.example`; the scripts read exported environment variables and do not automatically load that file. Region defaults to CA/CAD. Use a separate database/runtime for US/USD. Providers remain disabled.
