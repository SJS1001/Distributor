# Proposed domain, command and workflow contracts

Date: 2026-09-30. Status: planning proposal, not code or a final database schema. Supports [architecture](ARCHITECTURE.md), [requirements](REQUIREMENTS.md) and D-007–D-034. DEC-01–DEC-11 settle business semantics and the implementation route before contracts are frozen.

## Records and ownership

| Owner | Proposed records | References and invariants |
| --- | --- | --- |
| Identity/accounts | Organization, account, staff/buyer principal, grants | Account/site scope comes from authenticated grants. Never trust a caller-supplied role or account ID as authority. |
| Catalog/pricing | Product, UOM conversion, identifier alias, price policy, quote | Product/serial/location identifier types are distinct; quote captures policy/version/currency/tax inputs and expiry. |
| Procurement | Supplier, PO and expected receipt lines | PO line references a product and expected commercial quantities; inventory records the actual stock effect. |
| Inventory | Warehouse, bin, stock position, serial custody, movement, cost layer, reservation, transfer, count | One physical/custody state per serial. Immutable movement evidence explains every correction. Availability never counts quarantine/transit stock. |
| Orders | Cart, sales order/line, accepted commercial snapshot, backorder, credit exposure commitment | Accepted price/tax/terms remain explainable after policy changes. Supplied/canceled/open quantities reconcile to accepted/amended quantity. |
| Fulfillment | Pick/pack records, shipment/line, carrier booking reference, tracking, collection/delivery evidence | Shipment lines reference order lines and inventory allocation/serial IDs. Carrier tracking does not authorize stock return. |
| Billing | Invoice/line, credit/line, receivable, payment allocation, refund | Invoice links accepted commercial evidence and billing trigger; credits reference original document/tax evidence. Allocations/credits/refunds never exceed authorized balances. |
| Warranty/returns | Sold-serial coverage, claim, evidence, RMA/line, inspection and disposition | References original sale and eligible customer; inventory and billing own the resulting stock/money changes. |
| Integration | Provider/source binding, external ID map, import batch/reject, accounting delivery/effect receipt | Credentials stay outside business payloads; uncertainty, retry and reconciliation are explicit. |
| Platform | Audit entry, document metadata, outbox/inbox, leased work, command receipt | Audit binds actor, scope, reason, correlation and result; attachments use authorized retrieval and controlled storage. |

This is a logical record map. D-009 specifies tables, constraints, migrations and transaction interfaces for the selected stack. Foreign IDs are versioned references, not permission for a module to mutate foreign storage. Historical documents retain enough original facts to be understood if catalog/account data later changes.

Quantities and money use exact decimal or fixed-scale representations with explicit UOM/currency and rounding policy. No floating-point arithmetic or silent fractional-unit truncation. Date/time records distinguish business-effective time, recorded time and coverage/reconciliation cutoff. Policy version and timezone form part of the evidence when relevant.

## Command envelope and results

Current local identity operations are `user.create`, `user.update`, `user.password.reset`, `user.password.change`, `user.sessions.revoke` and `user.sessions.end-own`. Administrative writes reauthenticate the current administrator; target edits/resets/revocations require the displayed security revision and organization scope. Buyer accounts and warehouses must exist in that organization. Access/password changes end affected sessions atomically with the revision, receipt and audit. The last active administrator cannot be deactivated/demoted. Initial/reset password changes restrict workspace access until completed; current credentials/status are reread before session issuance. See [access semantics and remaining qualification](USER-ACCESS.md). Optional `/api/security/mfa/setup`, `/confirm` and `/disable` operations own encrypted TOTP enrollment/removal and single-use recovery factors; complete factor proof precedes session issuance. Setup has a scoped body retry key, while confirmation/removal end all sessions and return no reusable command cache entry. Password resets preserve factors; isolated restore invalidates copied recovery codes/pending setups and sessions. These local operations do not establish lost-device recovery or product-gate acceptance.

Recovery-code replacement adds self-scoped `POST /api/security/mfa/recovery/prepare` with exactly `{currentPassword, revision, key}` and response `{renewalId, expiresAt, recoveryCodes}`. Its encrypted ten-minute bundle is inactive and retryable with the same key/current revision. `POST /api/security/mfa/recovery/confirm` accepts exactly `{currentPassword, renewalId, code, recoverySaved}`; current password, saved acknowledgment and an existing unused factor authorize atomic replacement, revision advance and session revocation. It returns `{revision, sessionsEnded, sessionEnded: true}` and clears the calling cookie. The authenticator remains enabled, including for required roles. These routes require session/origin/CSRF checks and no-store responses; neither stores plaintext codes in ordinary command results. Interrupted confirmation is resolved by signing in with retained factor access, not by assuming rollback. See [replacement and limits](USER-ACCESS.md#replace-recovery-codes).

Authenticator replacement adds self-scoped `POST /api/security/mfa/replacement/prepare` with exactly `{currentPassword, revision, key}` and response `{replacementId, expiresAt, secret, recoveryCodes}`. Its encrypted ten-minute new secret/codes remain inactive until `POST /api/security/mfa/replacement/confirm` accepts exactly `{currentPassword, replacementId, currentCode, newCode, recoverySaved}`. Current password, saved acknowledgment, existing unused factor and six-digit new authenticator proof authorize atomic factor/code replacement, new replay boundary, revision advance and all-session revocation. Response is `{revision, sessionsEnded, sessionEnded: true}` with calling cookie cleared. MFA stays enabled for required and optional roles. These routes inherit session/origin/CSRF/no-store checks, purpose-bound ciphertext, expiry/revision/restore invalidation and persistent throttling. Recovery renewal and factor replacement replace one another's pending ID; ciphertext cannot cross-confirm. Interrupted confirmation requires sign-in to establish its outcome. No lost-device or administrator bypass is supplied. See [procedure and limits](USER-ACCESS.md#replace-authenticator).

Every mutating application operation carries authenticated actor/context, authorized organization/account/site scope, command name/version, idempotency key, correlation ID, target ID/revision where relevant, payload and required reason. Server-derived identity overrides claimed request fields. Browser/hardware scans resolve input and then invoke this same boundary.

Process in order: authenticate → authorize full object/scope → validate request shape/version → inspect same-scope idempotency receipt → evaluate current policy, revision and invariants for new work inside the owning transaction → commit business facts, durable response and outbox intent together. Recheck authorization before returning a cached result; a previous command receipt cannot leak another account's document. A committed retry returns its original policy snapshot/result rather than reapplying a changed policy. Scope keys by organization, principal or authorized workflow, command and policy-defined lifetime. Same key/different payload is a conflict; same key/same authorized payload returns the original committed result. Concurrent identical requests must resolve through one durable key/transaction boundary, not a separate unchecked lookup. D-010 defines retention and long-lived effect deduplication so expired request keys cannot repeat a financial/shipping effect.

Result contains command receipt ID, outcome, owning record IDs/revisions, current state, relevant quantity/money summary and pending external effect IDs. It distinguishes committed business intent from provider completion. Never claim a payment is settled because work was queued.

| Outcome/error | Expected behavior |
| --- | --- |
| Validation/unknown or ambiguous identifier | No effect; name the correctable field/identifier without exposing foreign data. |
| Unauthenticated/forbidden scope | No read/write/export effect; redact existence where appropriate; audit the denial. |
| Stale revision/state conflict | No partial effect; return authorized current revision and allow review/retry. |
| Insufficient stock/credit hold | No competing allocation/exposure escape; show allowed partial/backorder action under policy. |
| Idempotency payload conflict | Reject; do not silently reinterpret the previous request. |
| External pending/unknown/rejected | Preserve committed intent/evidence; lookup/reconcile uncertain outcome, then approve safe retry or correction. |
| Internal failure | Transaction rolls back uncommitted changes; client queries original command receipt after reconnect before resubmitting. |

Order acceptance must coordinate reservation and credit exposure without a race that accepts two orders beyond the agreed limit. D-009 chooses a transaction invoking owning interfaces or a durable held workflow; no order reports accepted/allocated until its required owning commitments exist. External payment/carrier calls are outside database transactions. A return disposition with multiple effects persists which owning steps completed and retries only unfinished steps.

Current transfer receiving requires a transfer/line ID, positive quantity, exact scanned serial (null for bulk), destination bin, condition, arrival evidence and a portion reference. The reference is unique per organization/line/portion; retries with another request key or receiver return the same stored result when the normalized details match, and conflicting reuse fails. The immutable manifest keeps original dispatched quantity/cost after destination stock moves again. Each receipt changes only its portion; the remainder stays unavailable in transit. Damaged/quarantined destination lots stay unavailable until an authorized disposition. Missing quantities are not silently written off or completed.

Current grants are checked before any cached command result is returned. A dispatch retry uses the original transfer's source permission even after stock arrives elsewhere; receiving retries still require destination permission. Legacy whole receipts are reconstructed from dispatch evidence without fabricating portion-level arrival records. Additive local reconstruction is tested; production upgrade/recovery qualification remains outstanding.

Current transit loss approval is a separate administrator task: transfer/line, current transit revision, positive quantity, manifest serial confirmation (null for bulk), unique loss evidence reference and reason. A missing arrival alone cannot close a transfer. Approval removes only the confirmed missing portion; normal arrival can still receive its unlost remainder. Found stock uses the loss ID, positive quantity, exact serial scan, unique recovery reference, destination bin, condition and evidence. Recovery never changes the original manifest or deletes the approved loss, and never reduces other unresolved transit quantities. It cannot exceed the unrecovered portion. A serialized recovery preserves the original stock identity; bulk recovery creates a separate destination lot at original cost.

For each line, dispatched quantity = ordinary arrivals + recovered quantity + still-in-transit quantity + unrecovered loss. Net loss cost is unrecovered quantity × original unit cost; remaining physical valuation plus net loss cost reconciles to opening stock cost before sales/count adjustments. Loss/recovery movements carry the original cost and evidence, but do not post an accounting expense or carrier claim settlement. Per-line loss references and per-loss recovery references deduplicate normalized content across request keys/administrators; conflicting reuse rejects. Current administrator authority and organization scope are rechecked before cached results. A stale transit revision blocks loss approval after arrival or another adjustment. Local transactions serialize arrival versus loss and competing recovery. All-resolved transfers with unrecovered loss display `reconciled-with-loss`; recovery can return that display to `received` without erasing history. The existing persisted whole-line flag denotes no unresolved transit in this case; loss records distinguish it from a received or unknown legacy arrival. A full loss leaves zero quantity/value in its original transit record for custody history.

This administrator approval policy is provisional engineering behavior. Operator review, configurable approver duties, accepted write-off/recovery accounting, actual provider claims and production migration/restore evidence remain required.

Current bulk cycle counts capture the stock ID, physical revision, quantity, unit cost, warehouse/bin/condition, opening actor/time and an organization-unique count reference. The snapshot does not freeze physical operations or reservations. A warehouse operator or administrator submits one immutable nonnegative quantity and observation reason; identical retries return its original result, conflicting observations reject. The observation alone creates no stock movement. An administrator approves a submitted count or rejects a draft/submitted count with a reason; approved/rejected decisions remain durable and cannot be changed by another request key. Normalized count references deduplicate the original opening snapshot across request keys.

Approval requires the physical revision still to match the cutoff and the observed quantity to cover current reserved quantities. A stale snapshot stays submitted until rejected; start a fresh count rather than overwriting changed stock. Transactional checks serialize approval against allocation, dispatch and another count. Correction records observed minus current quantity and its signed value at original unit cost; site/bin/condition remain unchanged. Serialized and transit quantities cannot be corrected through this bulk workflow. Neither approval nor the administrator-only direct adjustment creates an invoice or accounting entry. Audit evidence retains opening, observation and review actors/reasons/times. Administrator self-review and the direct adjustment path remain provisional defaults. The [saved organization count policy](COUNT-REVIEWS.md) can require a different administrator from both starter and observer and disable direct adjustments. New approvals review the current policy version; each new decision retains its policy snapshot. Configuration and count commands refresh persisted principal/grants/password restrictions before cached replies. Actual operating separation of duties remains to qualify; serialized discrepancies follow their separate custody review.

Count history and cached opening/observation receipts require current role and original snapshot-site authorization, including after the unit moves to another site. Revoking the original grant blocks historical replay even if a new destination grant exists. Multiple pending snapshots of a lot are permitted locally; approving one changes its revision and invalidates the others for approval. Real human cutoff procedures, reconciliation policy, large count batches and production fault/upgrade proof remain outstanding.

## Proposed lifecycle states

States may be projections of quantities and evidence rather than a single status column. D-001/D-004 define exact transitions and compensation authority. A closed record is not mutable merely because a later event is delivered.

| Aggregate | Normal path | Exception/correction rules |
| --- | --- | --- |
| PO | Draft → approved → partially received → received → closed | Unexpected delivery and supplier return link explicit decisions; closure does not erase remaining/rejected quantities. |
| Serial custody/condition | Receipt quarantine → usable → reserved → picked/packed → shipped; usable → transit → destination quarantine/usable | Return enters quarantine; repair/restock/scrap is approved. Custody and condition are separate dimensions; reservation never adds/removes physical units. |
| Transfer | Draft → dispatched → partially received → received → closed | Shortage/damage/open transit remains accounted for; cancellation after dispatch needs physical reconciliation. |
| Order line | Cart → quoted → accepted/held → allocated/backordered → supplied/canceled remainder | Quantities can have multiple simultaneous states; amendment keeps original snapshot/history; return does not rewrite supplied quantity. |
| Shipment | Planned → picking → packed → committed → carrier/collection → delivered/exception | Short pick/unpick before commitment; committed shipment correction uses a linked movement/return, not state reset. |
| Invoice/credit | Draft → issued → delivered; settlement derived from allocations | Issued document remains immutable; corrections are linked credits/replacements, not deletion or recycled numbering. |
| Payment/refund/effect | Requested → pending → verified success/rejected; pending → unknown → reconciled | Manual lookup may be required; rejected and unknown are distinct. No automatic second effect while outcome is unknown. |
| Claim/RMA | Submitted → under review → denied/approved → authorized return → received quarantine → inspected → disposition → resolved | Evidence, partial receipts and downstream failure visible; replacement has linked old/new serial ownership. |
| Import/accounting delivery | Prepared → validated → reviewed → applied/delivered → reconciled | Row rejects and corrections are auditable; no success if accepted source/destination totals disagree. |

## Access and audit proposal

Proposed permission sets: buyer (own account), warehouse receiver/picker (granted sites), inventory supervisor (approved adjustments/transfers), commercial staff (authorized pricing/orders), finance (documents/payment/credit), warranty reviewer (claims/disposition), administrator (grants/configuration), support operator (bounded diagnostics/recovery). Roles do not imply unrestricted account/site access. DEC-03/04/05/08 determines separation of approval duties and overrides; names here do not assign humans or grant privileges.

Apply the same checks to filenames/downloads, bulk search, serial history, price lookups, import/export and background work. Worker authority comes from its scoped service principal and persisted approved intent, not an inherited administrator context. Audit records preserve who acted, relevant before/after revisions, reason, rejected attempts and the chain to physical/financial/provider receipts. Document/file metadata and signed retrieval must be account/site authorized; label contents cannot disclose unrelated customer data.

## Customer residency choice — approved planning direction

Identity/accounts owns the regional selection and versioned account choice. Application storage starts in the declared CA or US region. Storage location and permission for a processor to handle minimum required data outside that region are separate facts. A customer can choose Stripe, QuickBooks, UPS, FedEx, USPS, Canada Post, Purolator and DHL Express independently; one choice never implies another. Stable IDs are `stripe`, `quickbooks`, `ups`, `fedex`, `usps`, `canada-post`, `purolator`, `dhl-express`. Historical family `carrier` entries authorize none of the named carriers; retain original receipts and require explicit versioned review rather than expanding them. Choices record eligibility and do not qualify or enable provider services. A region change requires a reviewed migration rather than a preference toggle.

Acceptance evidence identifies account, customer or authorized representative, named provider, disclosure version, reviewed processing locations, purposes/minimum fields, acceptance time and audit identity. Staff may record externally obtained acceptance with its evidence reference; staff acknowledgment alone does not establish customer consent. Disclosure changes require review before applying the new terms. Retention and consent requirements still need applicable vendor/business qualification.

Local IAM now owns immutable disclosures, current provider/region heads and acceptance evidence. Administrator `provider.disclosure.publish` requires expected previous ID (null for no head), unique version, public fields and private review evidence. `provider.disclosure.withdraw` requires current ID/reason. `account.residency` requires optional acceptance only for nonempty exceptions: exact selected disclosure IDs plus buyer basis for actual own-account buyers, or recorded basis with external representative/evidence for authorized staff. Choice/version/acceptance/audit/receipt commit together. Fresh authority precedes cached results; a cached historical result does not change the current head/choice. Acceptance ID/hash must match current terms before permission; no prior exception gains evidence automatically. Public and acceptance-history reads are scoped/bounded as described in [the runbook](PROVIDERS.md#reviewed-provider-disclosures). This is local engineering, not legal consent, vendor residency or production qualification.

`GET /api/accounts/:accountId/provider-acceptance-versions` accepts only optional positive safe integer string `after`, an existing accepted choice version in that organization/account. Descending version pages return at most 20 `{version,acceptedAt,providerCount}` rows and a string `next` when more exist. It checks fresh administrator/commercial/finance/support or own-account buyer authority before cursor lookup; warehouse access rejects. Newer versions stay outside older continuation pages. Strict/initial/unreviewed versions with no acceptance are absent, not reconstructed. The Customers history view uses the existing at-most-eight acceptance records and retained public documents, validates provider/hash equality, excludes private vendor review evidence and preserves failed pages/cancels unmounted reads. Historical acceptance changes no stock, orders, billing or current permission. [Local evidence](evidence/LOCAL-PROVIDER-HISTORY-2026-10-01.md) covers bounded synthetic behavior; production workload and actual consent remain unqualified.

Every new provider intent, outbound send, worker execution and reconciliation checks current authority and choice. Strict, declined or withdrawn choices deny the relevant external request while native ordering, stock, invoices and permitted manual operations remain available. Withdrawal cannot recall a request already in flight or data already transmitted; the disclosure and operator procedure must explain that limit and preserve historical receipts. Refund/accounting recovery must not bypass choice silently; unresolved required provider actions remain visible for authorized review.

Acceptance evidence must cover both CA/US selection, separate provider choices, another-account denial, revoked staff authority, queued work after withdrawal, disclosure-version changes and region-migration refusal. Physical application, backup, logs/support and provider processing residency require separate infrastructure/vendor evidence. See [provider qualification](PROVIDERS.md), D-008/D-024/D-027/D-034 and CH-07/CH-09; this contract does not qualify the implementation.

## Local supplier return contract — implementation checkpoint 2026-09-30

The implemented `purchase.return` task accepts an original purchase receipt, held stock lot, expected physical revision, quantity, exact serial (null for bulk), organization-unique return reference, reason and handover evidence. Current administrator authority is required before both fresh and cached results; the caller cannot supply a supplier, original cost or approver. Supplier identity comes from procurement's purchase record. Inventory follows its owned custody graph to the purchase movement and requires one matching origin, current stock state/revision and unreserved physical quantity. Split dispatch records its source lot; partial arrival/recovery links its resulting lot to that dispatch. Whole-lot movement preserves identity. No source/receipt connection is inferred from equal product, cost, quantity or warehouse; historical split lots missing source evidence remain ineligible pending reconciliation.

Procurement stores an immutable return receipt including original purchase/receipt/supplier, handover site, lot/serial, quantity/cost, actor/time, evidence and normalized input/result. Inventory removes quantity at the lot's original cost and records one signed `supplier.return` movement in the same owning command transaction. The cumulative receipt return cannot exceed its purchased quantity, including after a count gain. Purchased/received quantities and PO state remain unchanged. A normalized organization-wide return reference replays one result with the same evidence across keys/administrators/restart; changed evidence conflicts. Current role checks precede replay. Competing dispatch/return commands cannot consume the same stock.

Warehouse receipt views expose purchase provenance for currently held authorized lots and receipts originally received at their granted sites; original raw unit-ID lists are withheld. Return history is limited to granted handover sites. Serialized handover leaves a zero-quantity stock record with its original identity and permanent movement history; it has no value/availability and cannot be received as another new serial or through the sold-customer return path. Bulk remainder preserves bin/condition/cost. At the original handover checkpoint, supplier credit, replacement delivery, accounting posting and carrier settlement were separate pending work; no customer credit was created. The follow-up checkpoint below adds outcome evidence while actual external reconciliation remains pending. Administrator-only approval and recorded handover evidence are provisional operating policy awaiting responsible business review. Local tests do not verify a product gate.

## Supplier outcome observations and reviewed follow-up

Procurement owns `procurement_return_followups` and exposes `purchase.return.credit`, `.replacement`, `.void` and `.review`. Every command carries the original return ID, expected follow-up revision, organization-wide unique reference and retained evidence. Finance and administrators may record/review; commercial and warehouse roles may read, with warehouse reads restricted to the original handover site. Current active identity, actual grants and required password changes are checked before cached command results and history cursors. HTTP requires a session, CSRF and an exact payload shape.

Credit observations require positive integer cents in the organization's CAD/USD currency, without FX. They may differ from original stock cost; finance must reconcile differences separately. Replacement links require a separately received new purchase order from the same supplier for the same product. Active linked quantities cannot exceed original returned quantities or that delivery's received quantity across all returns. A link records receipt provenance, not present physical custody. It never receives inventory again. Original handover cost, purchase received totals, invoices, customer credits and cash remain unchanged.

References normalize NFKC/uppercase; identical original evidence replays the original result across keys/restart before stale-state checks, while changed details conflict. Current authority still precedes replay. Observations, owning event, audit and permanent command receipt commit atomically. SQLite write serialization protects revisions and global replacement capacity; local separate-process tests cover both boundaries. Old writers must be stopped before upgrade; mixed-version operation is unqualified.

Credit/replacement/void changes require an open follow-up. Voids target only an active credit or replacement on that return, retain the original fact and free its active replacement allocation. Reviewed closure requires explicit `reconciled` with at least one active outcome, or `no-remedy` with none. Reopening has null resolution; duplicate state transitions reject. Closure is a recorded finance review, not proof of settlement or ledger reconciliation. History returns at most 20 descending revisions, uses an existing scoped revision cursor and marks older voided observations even when the correction lies outside that page. Private input hashes/cached results are withheld. Current return listing and aggregate scans remain unqualified at production volume.

See the [supplier return runbook](SUPPLIER-RETURNS.md) and [bounded local receipt](evidence/LOCAL-SUPPLIER-FOLLOWUPS-2026-10-01.md). Approval duties, original supplier documents/custody, attachments, supplier ledger/accounting posting, actual vendor settlement, workload, migration/recovery/security and independent operator acceptance remain open. ## Local opening import contract — implementation checkpoint 2026-09-30

Migration owns versioned source manifests, immutable raw-input/report hashes, row rejects, administrator decisions and permanent source-to-stock mappings. `import.opening.preview` accepts source reference/hash/cutoff, organization region/currency, independent quantity/value totals, source rights/mapping acknowledgment and 1–500 exact-format rows. Catalog and inventory resolve exact SKU/site names through their owning APIs. Inventory validates active products, serial/bulk identity, original integer cost, condition and an empty product/site custody history. The dry run records evidence without writing stock. Duplicate source identities/serials, row issues or independent total mismatch block the entire batch.

`import.opening.decide` binds a decision/reason to the saved review fingerprint. Only current organization administrators may list/preview/review; cached results recheck that authority. Approval reassesses current custody/mappings/source identities inside the same command transaction, then invokes inventory's opening operation and records each mapping. Inventory alone creates units and `opening` movements. A stale review rejects rather than applying changed evidence; a late mapping/storage failure rolls back all stock/decision/command changes. Identical batch references and decisions deduplicate normalized evidence across keys/restart; conflicting reuse rejects. Correction creates a new immutable batch while retaining source namespace/row IDs. Rejection preserves the report and applies no stock.

The local stock path supports original-cost physical opening balances, including unavailable quarantine/damaged stock, without purchase receipts, invoices or accounting entries. Opening custody does not invent supplier purchase lineage. Source hashes/rights/cutoffs are supplied attestations requiring actual external evidence. Administrator self-review is provisional. See the [runbook](IMPORTS.md) for limits. Customer/catalog imports have bounded local implementation evidence in the [master import receipt](evidence/LOCAL-MASTER-IMPORTS-2026-09-30.md); matching preserves existing residency choices and new customers default to strict regional processing. ## Local billing documents contract — checkpoint 2026-09-30

Billing owns versioned party profiles, immutable issuance facts, stored PDF bytes and prepared download receipts. New invoice facts are captured in the issuance transaction; credit facts inherit original invoice identities and values. Legacy reconstruction explicitly marks missing historical identity/terms, and imported opening reconstruction retains original source totals/due dates/cutoff without claiming an original source PDF. Current cash/credits do not rewrite original document totals.
