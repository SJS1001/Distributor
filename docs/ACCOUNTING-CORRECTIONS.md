# Approved stock-cost account mapping corrections

Engineering continuation, 2026-10-03, following the owner's accepted [recommendations](MISSING-INPUT-RECOMMENDATIONS.md). This extends [original cost handoffs](ACCOUNTING-COSTS.md) with linked immutable account mapping corrections. It preserves original quantities, costs, artifacts, permanent movement claims and the reviewed cursor. It does not recalculate valuation. Preparation, approval, observation and download perform no provider requests; separately reviewed delivery uses the default-disabled [native journal controls](STOCK-JOURNAL-DELIVERY.md) and [protected journal command](STOCK-JOURNAL-TRANSPORT.md). All product tasks and gates remain NOT VERIFIED.

## Configure and prepare

Current internal finance/admin users open Billing, load a saved approved stock-cost review, then Load cost corrections. Configure a versioned policy with the customer's established valuation/finance basis, monthly periods, optional closed-through date, inventory account, movement-type offset accounts and responsible finance evidence. Example accounts are synthetic; the actual chart requires review. The first revision supplies `previousRevision: 0`; later revisions identify the exact current revision. A closed-through date cannot move backwards or be removed after closing. Policy history is immutable and hash-checked. This policy controls corrections only; it does not silently change original handoff policy or the customer's valuation method.

Prepare a correction identifying the original approved ID and SHA-256, current policy revision, permitted posting date, named ledger receiver, original external reference, independently verified outcome and evidence, and reason. The posting date must fall after any recorded close. Accounts must actually change; every nonzero original movement must map to a supplied offset different from inventory. The original journal amounts and movement identities remain exact and balanced using checked integer arithmetic.

| Verified original outcome | Saved plan | Additional evidence |
| --- | --- | --- |
| Posted | Reverse the exact original accounts/amounts, then replace with corrected accounts | Original ledger posting date; accountant review for an original date in a closed period |
| Unposted and cancelled | Corrected replacement only | Verified non-posting and cancellation; retain matching original receiver/acceptance identity if present |
| Unknown | Blocked review, no downloadable artifact | Outcome evidence remains unresolved; cannot approve |

A recorded original acceptance must match the supplied ledger receiver and external reference. Its later creation or any policy revision changes the frozen review and invalidates approval. A closed-period mapping correction requires responsible accountant evidence; this workflow does not perform retrospective restatement, write-downs, quantity changes, changes of valuation method or arbitrary financial adjustments.

## Independent decision and delivery

A different current internal finance/admin principal must approve or reject the exact saved review hash. Approval recomputes the plan against the intact original, current policy and receipt evidence inside the command transaction. One original can have only one first approved correction, and each approved predecessor can have only one approved successor. Competing drafts cannot approve competing replacements of the same predecessor. Unknown outcomes cannot be approved. Rejection retains evidence. Exact retries preserve the original request key and result, while changed input conflicts. Successful decisions create immutable canonical JSON plus a newline, including original hash, policy/evidence, reversal/replacement journals and preparer/reviewer identities and times. Server and browser validate its exact SHA-256 before download.

Download does not record delivery, ledger acceptance or posting. Retain the file and reconcile its separate reversal/replacement references through an approved ledger process. The ledger observation command below retains operator evidence. Default-disabled native journal delivery separately controls actual request ownership; independent finance reconciliation remains required. A fresh original acceptance is refused after an approved correction supersedes that original; existing original acceptance history and exact retries remain historical evidence. Original and correction downloads remain available under restore hold; new policies, preparations, decisions and ledger observations remain blocked. Browser operations discard responses after navigation/sign-out without undoing a committed native command.

## Retain separate ledger observations

Open an approved correction and Load ledger observations. Each existing reversal/replacement leg shows the approved receiver, region, currency, intended debit/credit totals in minor units and posting date. Record the receiver's journal or request reference and evidence for `unknown`, `posted` or `cancelled-unposted`. Posted evidence must identify the approved posting date; unknown/cancelled evidence has no posting date. The command binds the exact correction hash, leg and intended amounts. These amounts describe the approved journal, not a separately measured receiver balance. Evidence is an operator attestation, not vendor certification or automatic journal transmission.

An unknown observation can be resolved only with the same reserved receiver/reference and the exact current revision. Further unknown evidence appends another revision. Posted and cancelled observations are final; their bytes cannot be overwritten. Replacement posting evidence requires retained reversal posting evidence when the correction has a reversal. A cancelled or uncertain reversal does not permit a posted replacement. A posted reversal with an unknown or cancelled replacement remains visible as a partial correction needing finance reconciliation; no complete-posting success is inferred.

Reservations persist after cancellation. The same organization/receiver/reference cannot identify another correction leg, approved correction origin or fresh original acceptance; other organizations have their own namespace. Original receipt retries remain historical. Observation histories carry actor, time and SHA-256 and show the latest 100 revisions per leg; older rows remain retained in the store. Reads validate artifact identity, history hashes and reference reservations. Integrity checks detect inconsistent records; they do not protect against a privileged database administrator who can rewrite records and hashes.

An active browser retry retains the exact input/key after a lost reply. After Close, navigation or reload, reopen and load retained observations before deciding what evidence to add. Closing cancels response handling but never undoes a committed observation. Unsaved forms and an uncommitted generic attempt are not a durable browser recovery dossier. Current native finance authority and recovery hold are rechecked even before cached receipts; historical reads/downloads remain available under hold. Further changed-account corrections use the native/API and Billing chain procedure below. Valuation/quantity-error correction remains separate work.

## Correct the current settled replacement

Native finance/API callers may include optional `predecessor: { correctionId, contentHash }` in `accounting.cost.correction.prepare`. Keep the exact original approved packet ID/hash, and select the current approved correction's exact file ID/hash. Supply the current policy, a permitted new posting date, and outcome evidence matching its current replacement's receiver, external reference and original posting date. Existing first-correction requests omit `predecessor`; their retained bytes and receipts are unchanged. Billing provides a dedicated subsequent-correction review under each approved correction. Load the settled predecessor and current policy, supply the new date and independent evidence, review the fixed full snapshot and explicitly confirm the unchanged quantities/values. Preparing creates a draft requiring a different finance reviewer. If the settled posted replacement falls in a closed period, supply the accountant review before confirmation; a missing review keeps the form editable and creates no retained preparation.

Every predecessor leg must have final evidence. Each existing reversal must be posted; its current replacement must be posted or finally `cancelled-unposted`. Unknown, missing or cancelled reversal evidence refuses preparation. Pending or uncertain native attempts also refuse, even if an operator has manually recorded posting. Current native posting/cancellation must agree with finance evidence; older native attempts must be cancelled. Resolve uncertainty and exact-attempt cancellation/retries before preparing a different journal.

A posted replacement produces an exact reversal of that replacement's accounts and amounts, followed by the new mapped replacement. A finally cancelled replacement produces only the new mapped replacement. The original journal is never reversed again by a later correction. Accounts must change; an unchanged journal uses the separately reviewed retry procedure. Original movement identities, amounts, quantities, cost basis, files and cursor remain conserved.

Preparation freezes predecessor outcome revisions, attempt identities, native states, current policy and original receipt. Approval requires a different current finance/admin principal and recomputes those facts atomically. A changed predecessor, receipt or policy invalidates the review. Approval freezes new observations, retries and native delivery for the superseded predecessor. Historical exact receipts remain recoverable after current authority and restore-hold checks; reads, files and audit history remain available. Downloads validate the complete approved ancestor chain and fail closed on changed hashes, identities, review metadata or cycles. These integrity checks do not protect against a privileged administrator able to rewrite all evidence.

### Recover a subsequent preparation

Before sending, Billing saves the exact original body, key, policy and complete manual predecessor snapshot in same-browser organization/principal/original-scoped storage, with a SHA-256 fingerprint and storage read-back. A Web Lock coordinates tabs in that profile. The fixed review cannot be edited after confirmation. Missing coordination or damaged/empty/unavailable storage refuses replacement writes. A new tab cannot replace another retained preparation.

A lost, malformed or abandoned response retains that original attempt through reload. Reopen an approved correction under the same original and use Recover exact subsequent preparation. Recovery sends the same retained body/key; the native command returns the original cached draft while enforcing current authority and restore holds. The browser checks original/predecessor identity, current saved policy snapshot, frozen legs, preparer and review hash before clearing evidence. It does not generate a fresh key or silently discard a refusal. Reconcile unrecoverable evidence with an authorized operator. This storage is specific to subsequent preparation; existing first-correction, observation and decision recovery limitations still apply.

## Separately approve a retry after cancellation

A current finance/admin user may prepare a new attempt only after the current leg has final `cancelled-unposted` evidence. Supply a fresh receiver request reference and reason; the review binds the exact correction hash, current cancellation attempt/revision/evidence hash and current policy revision. The saved plan retains the exact approved journal date, amounts, currency, receiver and region. Unknown or posted outcomes cannot prepare retries. A changed policy or closed approved posting date refuses approval; this path cannot silently change the journal.

A different current finance/admin user reviews the frozen plan and SHA-256, then approves or rejects with a reason. Approval recomputes current evidence and reserves the new reference atomically. Competing drafts can exist, but only one approved child may replace a given cancelled attempt. Rejection keeps history without reserving its proposed reference. Approved references remain permanently reserved even after cancellation. Each new attempt has its own revision sequence and immutable observations; initial evidence and prior retries remain accessible. Active observation commands identify the current attempt ID and its separately approved reference. A new key for an earlier attempt refuses; exact historical receipts remain historical. Replacement posting still requires current verified reversal posting evidence.

Billing shows the active attempt, initial history and the latest 100 saved retry reviews; direct ID reads provide older reviews. Review controls use the same cancellable operation boundary and exact active request keys as observations. Lost replies may be retried with the original key/body. After navigation or reload, inspect saved history before acting. Native current authority and restore holds apply before cached replies. No journal is transmitted by preparing, approving or observing a retry; external cancellation and non-posting remain independently obtained operator evidence.
