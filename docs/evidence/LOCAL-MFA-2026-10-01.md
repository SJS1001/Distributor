Identity owns optional staff/buyer authenticator enrollment, replay counters and ten single-use recovery codes. Setup requires current password and security revision; activation additionally requires a current TOTP and recovery-save acknowledgment. Activation/removal atomically advances the revision and ends every session. Removal requires current password and unused factor proof; there is no administrator removal or lost-device bypass. Password resets retain the factor. Password-only login for enrolled users issues no session, actor or CSRF token. Required password changes block enrollment/removal until completed.

Native crypto independently implements RFC 4226/6238 SHA-1 TOTP, six digits, 30-second counters and bounded previous/current/next acceptance strictly after the last accepted counter. All six published SHA-1 eight-digit vectors and six-digit suffixes are covered. Secrets/pending bundles use AES-256-GCM with random IVs and organization/user/purpose binding under a separately configured 32-byte runtime key. Recovery codes each have 128 random bits and are persisted as hashes after activation. Secrets/codes/passwords are excluded from durable command/audit payloads and browser storage; HTTP responses use no-store. A pending encrypted bundle remains until replacement/activation/removal/restore, including after expiry; automatic expired-material cleanup is not implemented.

Setup retries recover the same encrypted material using the same user/revision key before its ten-minute expiry. A replacement invalidates earlier setup. Confirmation/removal end the calling session, so lost committed responses recover through a new factor login and inspection of actual state. Invalid/reused factor attempts survive transaction rollback in the shared eight-failure/15-minute email counter; correct password reauthentication during factor operations does not clear them. A complete login clears the counter. Local counters do not establish production abuse protection.

Restore discards pending enrollment, invalidates every recovery code that a snapshot could revive, retains the enrolled encrypted secret and rejects authenticator proofs through the restore's next counter. It also invalidates copied sessions. Wait for a later counter and retain the separate runtime key. Snapshot-era factors/grants still require source-cutoff review; subsequent changes cannot be inferred.
