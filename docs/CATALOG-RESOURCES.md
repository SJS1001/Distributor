# Catalog images and documents

Catalog owns product resources. Administrators can upload bounded JPEG/PNG/WebP equipment images, PDF literature/installation/maintenance documents, HTTPS document links, or HTTPS image links on `cdn.shopify.com`. Every resource starts as a draft. Publishing requires an explicit affirmation of ownership or permitted distribution with a retained explanation. No downloaded Gree research binary is imported automatically; source/model match and distribution rights still require review.

## Adding products and photographs

Signed-in administrators and commercial staff can use **Catalog · Add products** in the workspace sidebar or **Manage catalog** in public navigation. In Catalog, **Add product → Create product & add images** creates one native product and opens that exact product's Images tab. A failed catalog refresh or failed product read can be retried without creating another product. Existing products have an **Images & documents** shortcut in the product-name column.

Administrators choose **Images → Add image**, then **Upload image**, **Manufacturer image URL**, or **Choose from GREE library**. The library is the separately imported GREE.ca catalog; selecting a photograph copies its URL and provenance into a draft, without claiming a native SKU/model match. Changing the selected library product clears the chosen URL. Review alternative text, applicable models and permission before **Publish to eligible buyers**. Commercial staff can create products and review resources, but resource upload/edit/publication/retirement controls are administrator-only, matching server permissions.

Image URLs accept only absolute HTTPS links on `cdn.shopify.com`, with no credentials or custom port. Other hosts require a file upload. This matches the existing browser image-source policy; no CSP expansion is required. The server never downloads a linked image. It retains the URL with zero content bytes; browsers load the publisher's image with no referrer. Publisher availability and content changes are outside Catalog's control, and a failed image uses the Shop placeholder. External publisher processing is separate from the Canadian database storage boundary. Upload when a retained, normalized local copy is required.

The 2026-10-07 read-only pilot inventory contained 27 products, eight published family-page document links and **zero image resources**. The eight named GREE pilot products are the older greehvac.ca lineup; the GREE.ca import is a different lineup. No exact-model associations or photographs are attached automatically. Adding a resource through the reviewed workflow is what makes a photo appear in Shop.

The service authenticates a fresh actor and password-change status for every operation. Buyer list and byte retrieval recheck current product eligibility and active status through Catalog. Draft and retired resources remain staff-only; guessed IDs and an earlier authorized URL confer no continuing access. Mutations are administrator-only. Organization/product scope comes from the authenticated actor and Catalog, never a filename or client organization ID.

## Storage and lifecycle

Generated identifiers and metadata/content live together in Catalog-owned SQLite tables. No upload filename becomes a path. Images are decoded after signature/dimension admission and normalized to PNG, removing source metadata and trailing payloads. The gallery sorts by position then identifier; its first published image is the primary image. Meaningful alternative text is required. Changing metadata/order returns a published item to draft so staff explicitly republishes the reviewed revision. Replacement is a new upload; retirement preserves bytes, metadata and history. Version checks reject stale decisions. Idempotency keys recover each exact mutation receipt without applying it twice; changed input under an existing key is refused.

Limits: 8 MiB image input/output, 16 megapixels, 8192 pixels per axis; 16 MiB PDF input/output; 40 retained resources per product; 256 MiB retained content per organization. Retired resources count toward quotas. Lists exclude bytes. Byte retrieval checks both length and SHA-256 before returning a generated filename. Publication must have explicit permission evidence. Administrator history retains actor/time, reviewed metadata, permission/provenance and transitions; history update/delete are blocked by SQLite triggers. No automatic purge is implemented.

## Document quarantine and normalization policy

Arbitrary original PDF bytes never become buyer downloads. A fixed disposable child process parses each PDF using PDF.js with evaluation disabled and renders its pages into canvas images. A fresh pdf-lib document contains only those raster pages; original JavaScript, launch/open actions, annotations, embedded attachments, metadata and arbitrary object graphs are not copied. Original bytes are discarded; upload history retains their input digest. Successful normalization marks the draft's inspection approved, which allows the separate rights-based publication step. Failed parsing, encryption, oversized dimensions, excessive work or timeout refuse admission rather than making the original available. This content reconstruction policy does not claim antivirus certification.

Processing bounds: 100 pages, 4096 pixels per page axis, 16 million pixels per page, 80 million pixels per document, 256 MiB V8 heap, 20-second hard child-process timeout and 16 MiB bounded output. At most one PDF normalizer runs at a time to limit pressure on the shared pilot host. No paths, destinations, user commands, provider credentials or URLs are passed to the child. It has no need to fetch external content. Raster copies lose text selection/search, accessible text and interactive forms; administrators should use an explicitly permitted official HTTPS document link when preserving the original text/accessibility or serving a larger manual is necessary. Linked destinations are never fetched by the server and their content remains the external publisher's responsibility.

HTTP delivery must use authenticated routes, `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, generated content disposition names and restrictive CSP. Images can be inline; PDFs are attachment downloads. Quarantined bytes cannot be downloaded through application routes. HTTPS links reject other schemes and embedded credentials, and should open with `noopener noreferrer`.

## Backup, restore and operating limits

BLOBs provide coherent metadata/content backup through the existing SQLite snapshot/encrypted-backup path. There is no separate filesystem attachment directory to synchronize. Storage inherits the database's Canadian pilot boundary; this module creates no cloud bucket/provider account or alternate residency. The original resource tables were introduced in schema25; the pilot now runs schema31. The 2026-10-07 entry/image-link update requires no migration and does not import or publish product data. Follow the existing offline migration/activation runbook for future schema changes. Current update evidence: [catalog entry and images](evidence/CATALOG-IMAGES-2026-10-07.md). Local synthetic tests do not prove live backup recovery or business acceptance.

The process timeout bounds wall time and V8 heap bounds JavaScript allocations; native renderer allocations and OS-level network/process isolation need host-level containment qualification. The normalizer constructs no external URL sources, and PDF.js receives bytes only. Operators must keep the pinned parsers/renderers patched and qualify native process resource containment before broadly exposing arbitrary untrusted uploads. Upload is presently authenticated administrator-only. A stricter malware scanner can be added later without making original documents downloadable.

## Gree pilot references

`seedGreeFamilyReferences(app, actor, productIdsOrReceipt)` is an explicit asynchronous companion to the synchronous business seed. It accepts the original product ID array or a persisted seed receipt containing `productIds`, checks each ID against the fictional sample SKU, and publishes eight official Gree Canada family-page links through the normal resource commands. Repeating the helper replays its command receipts; it does not recreate business records. The three generic accessories receive no Gree references.

These are labelled family references, not verified exact-model manuals. The manufacturer pages were researched in `docs/catalog/gree-source-library.json`; linked SharePoint files remain individually unverified and the first manual retrieval was denied by the publisher. No Gree images or manual binaries are seeded or redistributed. Exact capacity, voltage, revision, model matching and binary redistribution permission remain unresolved. This source helper does not itself execute against a live pilot.
