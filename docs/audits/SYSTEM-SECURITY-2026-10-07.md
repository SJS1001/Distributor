## Confirmed finding SEC-01 — P2: rotating login identifiers bypass availability bounds

At baseline, `src/server/iam.ts:401` inserted an attempt row for each failed identifier, while `src/server/iam.ts:411–446` limited only the submitted email to eight failures per fifteen minutes. Every previously unseen identifier reached synchronous scrypt before failure. There was no transport/shared calculation budget and expired unknown identifier rows were retained indefinitely.

An unauthenticated client allowed to send same-origin API requests could continuously rotate identifiers to consume event-loop CPU and persistent rows. This is an availability defect; the equal-cost unknown-account calculation correctly avoids a credential existence timing shortcut and is preserved.

Reproduction against the baseline: 24 different unknown identifiers through `POST /api/login` all returned 401 in approximately 639 ms and created 24 attempt rows. After expiring those rows and submitting another new identifier, all 24 expired rows remained. Repeated requests to one account would reach 429, so the prior single-account tests did not expose the rotating-identifier case.

The final correction is in [iam.ts](../../src/server/iam.ts) (constants at line 81; admission at line 428), and the [HTTP login handler](../../src/server/http.ts) (line 2333):

- Fixed windows start at the first admitted attempt: 180 password calculations per shared SQLite store per 60 seconds, and 60 per qualified peer per 60 seconds. Successful calculations count too. Native logins share the store budget; HTTP adds a peer budget.
- The existing eight failed attempts per account per fifteen minutes remains. An already locked account is refused before admission and hashing. A peer that is already blocked spends no additional shared budget.
- Peer budget keys store a digest, not a plaintext address. Internal counter keys exceed the maximum accepted email length, preventing a supplied identifier from selecting or clearing them. Successful authentication clears only the account row.
- Admission removes at most 128 expired rows, and caps attempt storage at 8,192 rows. Account and transport slots are admitted under one SQLite transaction before hashing. A zero-failure account reservation is incremented on failure and deleted on success.
- Failure insertion also checks capacity atomically: another successful login can remove a reservation while a calculation is running. At full capacity, a new failure row is not recreated; the admitted calculation has already spent transport budget and later logins requiring new rows are refused. Existing account rows still accumulate failures.
- Throttled session reauthentication reserves its account failure slot before hashing, with the same bounded cleanup/cap and no login transport-budget charge. This preserves its eight-failure limit when attempt storage is saturated; ordinary session reads continue. Final self-review found and corrected this interaction with the capacity guard.
- The peer margin permits substantially more legitimate shared-NAT attempts than the individual account limit. Sustained exhaustion can temporarily refuse legitimate login attempts, including successful credentials; this is the explicit availability/security tradeoff of bounded synchronous password work. Session-authenticated business requests do not consume these login budgets.
- The HTTP peer comes from the socket by default. Spoofed forwarding headers cannot rotate it. Explicit Fly qualification uses the existing validated client-address boundary and refuses a missing trusted address. Actual ingress stripping and proxy topology remain deployment qualification work.

Independent domain review reproduced the first implementation's non-atomic reservation: two SQLite connections admitted the last account slot and retained 8,193 rows. The final reservation reduced that same reproducer to 8,192. A further deterministic regression interleaves an incorrect known-account calculation, a concurrent successful login clearing its reservation, and an unknown identifier consuming the freed slot; the final failure cannot exceed the cap.

Regression coverage: [system-security-login.test.ts](../../tests/system-security-login.test.ts) verifies rotating identifiers, hash-call admission, spoofed headers, another peer's successful login, restart persistence, distributed/native shared admission, fixed-window expiry, account lockout independence, bounded cleanup, capacity refusal, trusted Fly handling, both concurrent SQLite races, and saturated reauthentication retaining its account limit while refusing work before hashing.

## SEC-02 — Customer history retains cached private rows after a current authority denial (P2, fixed)

An additional static pass confirmed that the previous [customer-record.tsx](../../src/web/customer-record.tsx), `HistoryList` catch at line 668, only set the read error. Previously loaded orders, invoice balances and payment source/amount rows, plus the retained paging cursor, remained visible after a current non-aborted 403 or 404. Reproduction: load a customer history page with a next cursor, remove the relevant current read authority, then request the next page. The server denies the read while the component continues rendering prior data and its Load more control. A session-ending 401 also triggers the application's global sign-out handler; persistent 403/404 behavior is the clearest affected path.

Required narrow correction: inside the existing non-aborted catch, clear `items` and `next` for `RequestError` statuses 401, 403 and 404. Retain rows and cursor for transient network/5xx failures, and preserve the aborted-request guard so a stale denial cannot erase current records. Contacts and pricing already clear their authorized values on these statuses. This is a browser disclosure after explicit authority loss, not a newly confirmed native API authorization bypass; the scoped order/billing authority suites remain separate API evidence.

The UI owner applied that correction without changing the native API. Root ran the final [system-polish-customer browser suite](../../tests/system-polish-customer-browser.ts), including the parameterized 403/404 regressions at line 810, against local production bundle `index-CJgo2XAO.js`: **28 passed, 0 failed**, Chromium and WebKit, 23.7 seconds. Each denial case first loads private history and a cursor, proves a 503 retains both, retries the exact cursor successfully to append another row, then proves the denied next read removes both rows, the table and Load more while preserving the error and Retry. This lane inspected the correction and receipt; it did not execute that browser run. Root's private receipt is `/tmp/distributor-system-final-customer-history-verified.log`, with local artifacts under `local-evidence/system-final-customer-history-verified`. Synthetic browser response interception proves the UI retention/clearing behavior; existing scoped native authority tests remain the separate server boundary evidence.
