# Catalog retirement and reactivation

Local engineering, 2 October 2026. Product acceptance remains pending. See [the local receipt](evidence/LOCAL-CATALOG-LIFECYCLE-2026-10-02.md), [customer pricing](CUSTOMER-PRICING.md) and [task/gate definitions](TASKS.md).

Commercial staff and administrators can search the staff catalog, review a product and retire or reactivate it with a reason. Other staff can read the catalog; buyers receive their separate customer-priced selection. Catalog pages return at most twenty descriptors and retain SKU/id continuation with literal name/SKU search and active, retired or all filters. The projection excludes organization IDs. Search and status survive page continuation; a successful command refreshes the default active view.

Review includes current SKU, name, serial flag, base price, tax and status. `product.retire` and `product.reactivate` accept `productId`, `expectedHash` and `reason`. The hash binds the current product and latest retained lifecycle receipt. A retire/reactivate cycle invalidates an older review even when the product fields return to their original values. Native command transactions recheck persisted current permissions and required password status before both cached results and new effects. An exact retry recovers its original outcome; changed input with the same key refuses. After a lost response, retry with the identical reason and retained review before changing the request. If the review is stale, cancel and reopen.

Retirement removes the product from new customer selection and refuses new quotes and acceptance of previously prepared, unaccepted quotes. Already accepted orders retain their native stock allocations and fulfillability. Previously accepted quote retries recover the same order. Retirement changes only catalog activity and writes platform command/audit evidence; it does not delete stock, price tiers, purchase commitments, invoices, warranty records or saved carts. Existing unavailable-cart review governs removal before a new quote. Reactivation retains the same product identifier/SKU and current prices, enabling fresh quotes again. This is a customer-ordering availability control; it does not define a separate purchasing discontinuation policy. Saved and new receipt drafts can fulfill an existing purchase commitment for a retired product, retaining exact purchase-line SKU, serial, quantity, cost and current-authority checks. See [retired-product receiving evidence](evidence/LOCAL-RETIRED-RECEIVING-2026-10-02.md).

`GET /api/catalog/products/:id/review` returns a fresh reviewed descriptor/hash. `GET /api/catalog/products/:id/history` returns at most twenty lifecycle receipts with durable audit sequence continuation, current commercial authority and organization/product scope. Each receipt retains the before-product descriptor, old/new activity, actor, recorded time, reason and reviewed hash. No new database schema or migration is introduced. Malformed recent retained evidence refuses review rather than silently regenerating it. The history dialog loads older pages without closing. Navigation cancels pending catalog review/history reads.

Live catalog traversal is not an immutable snapshot. Rows can change between pages; refresh for current status. Bounded returned rows do not establish database scan/sort, writer contention, accumulated browser memory or production throughput limits. History review checks the recent page, not every older receipt; database corruption and operational audit retention require separate qualification.
