# Transfer queue

Inventory exposes `transferPage(actor, { state?, after? })` and authenticated `GET /api/transfers/page`. A response contains `items` (at most twenty transfer headers with their existing custody details) and `next` (a continuation token or null). Omit `state` for all states, or choose `transit`, `partially-received`, `partially-reconciled`, `received` or `reconciled-with-loss`.

Current persisted administrator, warehouse or support authority and the password-change requirement govern every read. Administrators see their organization; other permitted staff see transfers involving a currently granted source or destination warehouse. Empty grants return an empty first page. Organization and warehouse scope are applied in SQL before the twenty-header boundary, and details are expanded only for returned headers. Native receipts, losses and recoveries determine the live state filter before that boundary.

Headers sort by creation time descending, then insertion position descending. Tokens bind their purpose, version, organization, sorted current warehouse grants and selected state. Changed scope or filter requires a fresh first page. Invalid/noncanonical tokens and missing or inaccessible anchors refuse continuation. An anchor changing state still permits continuation with the original state filter; later pages observe current facts rather than a frozen multi-request snapshot.

The Inventory browser uses this page API. It replaces the visible table with at most twenty headers and retains only continuation tokens for Older/Newer transfers. The transfer reference identifies otherwise identical routes. Transfer state selects the five live states or all states; changing the filter starts at its first page. Refresh transfers keeps the selected state and restarts at the first page. Application Refresh or a successful transfer command resets the queue to the first page of all states.

Pending and failed page reads clear the previous rows and their change controls. Retry transfer queue repeats the exact failed state, cursor and page trail; the error focuses Retry and successful navigation focuses the Transfers heading. A newer filter/read, navigation, application refresh, sign-out or unmount abandons the older response. Empty results explain the current state and warehouse scope. Support staff have read controls only; existing native receipt, loss and recovery permissions and command behavior remain in force. The legacy `transfers(actor)` and `/api/transfers` operations retain full-list compatibility for other callers.

Per-transfer line and receipt/loss/recovery histories are still unbounded. Derived-state scans, existing query/index costs, the read transaction's writer reservation, changing records between pages and production-scale qualification remain limitations. No schema, dependency, workflow, transfer mutation or accounting policy changes. This is partial inventory engineering; all product gates remain NOT VERIFIED.
