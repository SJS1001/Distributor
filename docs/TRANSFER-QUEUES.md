# Transfer queue

Inventory exposes `transferPage(actor, { state?, after? })` and authenticated `GET /api/transfers/page`. A response contains `items` (at most twenty transfer headers with their existing custody details) and `next` (a continuation token or null). Omit `state` for all states, or choose `transit`, `partially-received`, `partially-reconciled`, `received` or `reconciled-with-loss`.

Current persisted administrator, warehouse or support authority and the password-change requirement govern every read. Administrators see their organization; other permitted staff see transfers involving a currently granted source or destination warehouse. Empty grants return an empty first page. Organization and warehouse scope are applied in SQL before the twenty-header boundary, and details are expanded only for returned headers. Native receipts, losses and recoveries determine the live state filter before that boundary.

Headers sort by creation time descending, then insertion position descending. Tokens bind their purpose, version, organization, sorted current warehouse grants and selected state. Changed scope or filter requires a fresh first page. Invalid/noncanonical tokens and missing or inaccessible anchors refuse continuation. An anchor changing state still permits continuation with the original state filter; later pages observe current facts rather than a frozen multi-request snapshot.

The Inventory browser uses this page API. It replaces the visible table with at most twenty headers and retains only continuation tokens for Older/Newer transfers. The transfer reference identifies otherwise identical routes. Transfer state selects the five live states or all states; changing the filter starts at its first page. Refresh transfers keeps the selected state and restarts at the first page. Application Refresh or a successful transfer command resets the queue to the first page of all states.

Pending and failed page reads clear the previous rows and their change controls. Retry transfer queue repeats the exact failed state, cursor and page trail; the error focuses Retry and successful navigation focuses the Transfers heading. A newer filter/read, navigation, application refresh, sign-out or unmount abandons the older response. Empty results explain the current state and warehouse scope. Support staff have read controls only; existing native receipt, loss and recovery permissions and command behavior remain in force. The legacy `transfers(actor)` and `/api/transfers` operations retain full-list compatibility for other callers.

## Retained dispatch recovery

Dispatch transfer saves the exact source unit/revision, quantity, destination, reason and request key before transport, with the original source/bin and product description. Storage is scoped to the organization and staff account and retains only the chosen destination. An uncertain reply survives closing, navigation, reload and signing back into the same account. Review retained transfer dispatch opens a fixed read-only review; Retry exact transfer dispatch reuses the original body and key. Do not dispatch the physical stock again. A confirmed receipt describes the original operation; inspect current stock and transfer history before further physical work.

Web Locks coordinate submissions from tabs sharing this browser. Damaged/unwritable storage, missing locks and changed reviewed evidence block transport. Malformed replies and cleanup failures preserve the original attempt. Known native pre-effect validation refusals permit correction; state/quantity refusals require closing and refreshing before reviewing current stock. Authority and uncertain failures retain exact recovery. Native current source grants are checked before cached results, including after another operator changes the source quantity/revision. Exact retries preserve original quantity, serial identity and cost without a second dispatch.

This protects retained evidence in the same browser profile. Cleared storage, other browsers/devices and uncertain dispatches made before this recovery feature require separate reconciliation; their original bodies cannot be reconstructed from an older generic request key. Shared-device retention/protection, physical custody and operator procedures remain unqualified. Native commands, costs and schema are unchanged. See [local dispatch-recovery verification](evidence/LOCAL-TRANSFER-DISPATCH-RECOVERY-2026-10-02.md).

## Retained arrival recovery

Receive transfer now uses a dedicated review. Before transport, it saves the exact quantity, scanned serial, arrival reference, bin, condition, reason and request key with the original transfer description in browser storage scoped to the organization and staff account. An uncertain reply retains this attempt across closing, navigation, reload and signing back into the same account. Review retained transfer arrival opens a read-only copy; Retry exact transfer arrival reuses the original body and key. Do not receive the physical stock again. A confirmed receipt describes the original operation; review current stock and history before further physical work.

Web Locks coordinate submissions from tabs sharing this browser. Unreadable or unwritable storage and missing lock support block transport. An opened review cannot be silently replaced by a storage event, and changed evidence is preserved rather than overwritten or cleared. Known native pre-effect validation, serial or reference refusals permit correction; state/quantity refusals require closing and refreshing before a new stock review. Authority failures and uncertain responses retain the exact attempt. Native current destination grants are checked before cached results. An original receipt can be confirmed after another receiver changes current remaining stock, including an already-recorded identical arrival reference; it creates no second arrival.

This protects only retained evidence in the same browser profile. Cleared storage, shared-device retention/protection, other browsers/devices, real scanning/custody and operator procedures remain unqualified. Native commands, costs and schema are unchanged. See [local arrival-recovery verification](evidence/LOCAL-TRANSFER-ARRIVAL-RECOVERY-2026-10-02.md).

## Retained loss approval and found-stock recovery

Administrators review transit losses and found stock in dedicated dialogs. Each operation retains its exact submitted quantity, scanned serial, evidence reference, reason and request key before transport. Loss approval also retains the original transit revision; found-stock recovery retains its original approved loss, destination bin and condition. Separate organization/account storage keys keep the two operation types independent.

An uncertain reply survives closing, navigation, reload and signing back into the same account. Review retained transfer loss approval or Review retained found transfer stock recovery opens a fixed read-only review. Retry exact reuses the original body and key. Do not repeat the physical write-off or receipt. The confirmed receipt describes the original operation; inspect current custody and history before additional work.

Web Locks coordinate submissions within this browser profile. Damaged/unwritable storage, missing locks and changed reviewed evidence block transport. Storage events cannot replace an open review. Malformed successes, cleanup failure, reference conflicts, authority failures and uncertain replies retain exact recovery. Native pre-effect validation or serial refusals permit correction; state, quantity and revision refusals require closing and refreshing Inventory before a new review. Current native administrator authority is checked even before a cached receipt is returned. A historical receipt after another operator's loss/recovery creates no second stock change and preserves serial identity and original cost.

This protects retained evidence in the same browser profile. Cleared storage, older uncertain generic attempts, shared-device retention/protection, other browsers/devices, physical custody and operator procedures remain unqualified. Native commands, schema, dependencies and workflows are unchanged. See [local loss/recovery verification](evidence/LOCAL-TRANSFER-LOSS-RECOVERY-2026-10-02.md).

Per-transfer line and receipt/loss/recovery histories are still unbounded. Derived-state scans, existing query/index costs, the read transaction's writer reservation, changing records between pages and production-scale qualification remain limitations. No schema, dependency, workflow, transfer mutation or accounting policy changes. This is partial inventory engineering; all product gates remain NOT VERIFIED. See [native verification](evidence/LOCAL-TRANSFER-PAGING-2026-10-02.md), [browser verification](evidence/LOCAL-TRANSFER-SCREEN-2026-10-02.md) and [implementation status](IMPLEMENTATION.md).

## Initial loading and retained reviews

A retained arrival, dispatch, loss approval or found-stock recovery review can open while the initial Inventory transfer queue is loading. Completing that read preserves the same fixed review and keyboard focus. Organization/account or selected-operation changes still establish a new review identity; explicit refresh clears selected current-stock reviews. Retained evidence remains fixed, and current native authority governs recovery. See [controlled local verification](evidence/LOCAL-TRANSFER-REVIEW-LOADING-2026-10-02.md).
