## Capability and ownership

Only `src/server/canada-post-test.ts`, new `src/server/canada-post-evidence.ts`, new `tests/canada-post-evidence.test.ts` and this document change. The new module imports core canonical/hash/error primitives and type-only native intent/address contracts. It performs no filesystem, database, network or credential lookup. No import, receipt, generation, authorization, provider account reservation, schema, runtime registration or HTTP mechanism is implemented.

The extracted functions are structural and deterministic prerequisites:

- `captureCanadaPostAccountBinding(value: unknown)` strictly captures the historical non-secret account descriptor. Exact top-level fields are orgId, warehouseId, testApplication, customerNumber, contractId, company, shippingPoint and ordered services. It checks the existing test marker, text/numeric-string bounds, Canadian pickup postal code or deposit-site form, 1–20 unique reviewed services and supported domestic codes. Shipping-point and service records reject extra fields; records reject inherited/accessor/non-data fields, and service arrays reject holes, extra properties and accessor entries. Credentials, tokens and arbitrary keys fail instead of being silently removed. The returned object and nested point/services are detached and frozen; service order and original supported text are retained.
- `canadaPostConfigurationHash(config)` computes the existing canonical non-secret hash, excluding clientId/clientSecret. It is a **compatibility hashing primitive**, not the strict descriptor parser: it preserves other legacy constructor-accepted extra fields in the hash. Historical untrusted input must first pass `captureCanadaPostAccountBinding`. Do not use an opaque hash as account evidence, and do not feed arbitrary secret-bearing metadata into the compatibility primitive. No credentials or config object are returned by it.
- `reviewCanadaPostShipment(config, intent, groupId, configurationHash?)` contains the original deterministic native-intent/review-hash checks, Canadian contacts, mapped service, shipping point and ordinary parcel limits, then creates the same customerRequestId and complete request body. Its default computes the hash; the live client supplies its constructor-captured hash as the final compatibility argument. This preserves historical request identity even if caller-owned, previously accepted extra metadata changes later. That optional argument is trusted client composition, not an offline evidence assertion: future offline callers must use a strictly captured descriptor and its computed hash, never a claimant-supplied override. The result contains fresh nested request data, with no references into the intent or configuration.
- `captureCanadaPostShipmentDetails(config, review, observation, value)` extracts the exact existing detail comparisons against the constructed review and captured shipping point. Observation supplies the already captured tracking/status identity; supported tracking/status are checked, and matching detail fields produce a fresh primitive summary. It keeps the original recipient/contact/parcel/reference/settlement checks and refusals for customs, notifications, nonempty options, return specification, transmission instruction, quickship and nonordinary parcel flags. Existing permitted empty defaults and unrelated provider metadata remain permitted. This is not a complete generic provider JSON schema.

The latter functions accept typed reviewed inputs. They do not authenticate a supplied review, configuration, snapshot, observation or optional compatibility hash. A coherently rehashed altered native customer is deliberately shown to pass the pure intent consistency check: current native ownership must be established separately by the future owning operation. Likewise, a matching `transmitted` detail can be structurally compared for the existing lookup/manifest path; this helper does not promote it to any native state. Creation still rejects transmitted responses in its unchanged response-identity check before fetching details.
