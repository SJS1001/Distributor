Warehouse staff with the current shipment site, or administrators under the existing administrator policy, can open **Review carrier booking** for a packed ordinary carrier shipment. Review the immutable packed destination and enter actual structured US/Canadian origin and destination, service, contact details and positive whole parcel dimensions in millimetres and weight in grams. No carrier is preselected. Confirm that the destination matches the packed address and the origin belongs to this warehouse. Named current customer acceptance and recorded disclosures are required separately. Preparation creates no external request, stock movement, cash or invoice.

Only one uncanceled booking may exist for a shipment. An unsent pending booking may be canceled with the exact review hash and a reason; its record remains in history. Cancel an unsent pending booking before using manual fallback. Unknown outcomes must be looked up; never resend or create another booking. Booking itself does not ship stock or issue an invoice.

## Explicit sandbox startup configuration

The server entry point calls `configuredCarriers` with exported environment variables. `.env.example` is a reference, not an automatically loaded file. `CARRIERS_ENABLED` defaults to absent/false. When false, subordinate carrier configuration is ignored and no client is constructed. When true, flags must be exactly `true`/`false`, at least one of `UPS_SANDBOX_ENABLED`, `FEDEX_SANDBOX_ENABLED`, `USPS_TEM_ENABLED` or `CANADA_POST_TEST_ENABLED` must be true, and `CARRIER_ORG_ID` must identify an existing organization in this regional database. This switch is independent of `PROVIDERS_ENABLED`, which controls payment/accounting access; carrier-only startup needs no Stripe/QuickBooks keys or finance worker. Unknown flags, incomplete selected credentials or unsupported service/contact configuration fail startup without revealing supplied values.

For UPS supply `UPS_CLIENT_ID`, `UPS_CLIENT_SECRET`, six-character uppercase alphanumeric `UPS_SHIPPER_NUMBER`, `UPS_SHIPPER_JSON` and `UPS_SERVICES_JSON`. The shipper JSON requires exactly `name`, `line1`, `line2` (empty allowed), `city`, `province`, `postalCode`, `country` (`US`/`CA`) and `phone`. The service array requires exactly `service` and string `code` in each entry. For example, a synthetic mapping is `[{"service":"Reviewed ground","code":"03"}]`; the text must match the booking review exactly. The registered shipper contact is separate from the actual warehouse origin in each review.

For FedEx supply `FEDEX_CLIENT_ID`, `FEDEX_CLIENT_SECRET`, nine-digit `FEDEX_ACCOUNT_NUMBER`, `FEDEX_COUNTRY` (`US`/`CA`), `FEDEX_PICKUP_TYPE` (`DROPOFF_AT_FEDEX_LOCATION` or `USE_SCHEDULED_PICKUP`) and `FEDEX_SERVICES_JSON`. Each service entry requires exactly `service`, `code` and boolean `residential`; for example `[{"service":"Reviewed ground","code":"FEDEX_GROUND","residential":false}]`. Existing domestic ground/residential constraints apply; an existing pickup arrangement is configured, no pickup is purchased. No coercion, default service, endpoint override or production carrier is selected.

JSON must be compact, without control characters, at most 16,384 characters; arrays contain 1–20 unique exact reviewed services. Credential/text fields use the existing bounded protocol validation. Shipping country describes the domestic service and is distinct from the database residency region. One startup binding per enabled carrier serves the configured organization; other carriers/accounts require an additional qualified implementation/configuration design, not a browser override. Supply real account configuration only through an approved secret/configuration store after authorization and vendor review; never commit secrets or customer addresses.

Construction validates and captures configuration without authentication, network calls, credential persistence, booking, pickup, stock change or background carrier jobs. Later environment changes cannot reroute the process; restart to change bindings. Restart does not resend retained bookings.
