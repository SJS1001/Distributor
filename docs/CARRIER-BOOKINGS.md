# Reviewed carrier booking coordination

Local implementation, 2026-10-01. All 44 tasks and 10 product gates remain NOT VERIFIED; the full system is incomplete. No actual carrier adapter, account, service, request, label printing or physical handover is qualified by this checkpoint.

Warehouse staff with the current shipment site, or administrators under the existing administrator policy, can open **Review carrier booking** for a packed ordinary carrier shipment. Review the immutable packed destination and enter actual structured US/Canadian origin and destination, service, contact details and positive whole parcel dimensions in millimetres and weight in grams. No carrier is preselected. Confirm that the destination matches the packed address and the origin belongs to this warehouse. Named current customer acceptance and recorded disclosures are required separately. Preparation creates no external request, stock movement, cash or invoice.

Only one uncanceled booking may exist for a shipment. An unsent pending booking may be canceled with the exact review hash and a reason; its record remains in history. A successor preparation must identify the exact latest canceled booking. Pending, running and unknown bookings block manual handover and packing void. Cancel an unsent pending booking before using manual fallback. Unknown outcomes must be looked up; never resend or create another booking. A confirmed booking requires its exact carrier identifier and tracking for separate physical handover. Booked packing cannot be voided until carrier voiding is qualified. Booking itself does not ship stock or issue an invoice.

## Explicit sandbox startup configuration

The server entry point calls `configuredCarriers` with exported environment variables. `.env.example` is a reference, not an automatically loaded file. `CARRIERS_ENABLED` defaults to absent/false. When false, subordinate carrier configuration is ignored and no client is constructed. When true, flags must be exactly `true`/`false`, at least one of `UPS_SANDBOX_ENABLED` or `FEDEX_SANDBOX_ENABLED` must be true, and `CARRIER_ORG_ID` must identify an existing organization in this regional database. This switch is independent of `PROVIDERS_ENABLED`, which controls payment/accounting access; carrier-only startup needs no Stripe/QuickBooks keys or finance worker. Unknown flags, incomplete selected credentials or unsupported service/contact configuration fail startup without revealing supplied values.

For UPS supply `UPS_CLIENT_ID`, `UPS_CLIENT_SECRET`, six-character uppercase alphanumeric `UPS_SHIPPER_NUMBER`, `UPS_SHIPPER_JSON` and `UPS_SERVICES_JSON`. The shipper JSON requires exactly `name`, `line1`, `line2` (empty allowed), `city`, `province`, `postalCode`, `country` (`US`/`CA`) and `phone`. The service array requires exactly `service` and string `code` in each entry. For example, a synthetic mapping is `[{"service":"Reviewed ground","code":"03"}]`; the text must match the booking review exactly. The registered shipper contact is separate from the actual warehouse origin in each review.

For FedEx supply `FEDEX_CLIENT_ID`, `FEDEX_CLIENT_SECRET`, nine-digit `FEDEX_ACCOUNT_NUMBER`, `FEDEX_COUNTRY` (`US`/`CA`), `FEDEX_PICKUP_TYPE` (`DROPOFF_AT_FEDEX_LOCATION` or `USE_SCHEDULED_PICKUP`) and `FEDEX_SERVICES_JSON`. Each service entry requires exactly `service`, `code` and boolean `residential`; for example `[{"service":"Reviewed ground","code":"FEDEX_GROUND","residential":false}]`. Existing domestic ground/residential constraints apply; an existing pickup arrangement is configured, no pickup is purchased. No coercion, default service, endpoint override or production carrier is selected.

JSON must be compact, without control characters, at most 16,384 characters; arrays contain 1–20 unique exact reviewed services. Credential/text fields use the existing bounded protocol validation. Shipping country describes the domestic service and is distinct from the database residency region. One startup binding per enabled carrier serves the configured organization; other carriers/accounts require an additional qualified implementation/configuration design, not a browser override. Supply real account configuration only through an approved secret/configuration store after authorization and vendor review; never commit secrets or customer addresses.

Construction validates and captures configuration without authentication, network calls, credential persistence, booking, pickup, stock change or background carrier jobs. Later environment changes cannot reroute the process; restart to change bindings. Restart does not resend retained bookings. UPS unknown outcomes require the existing read-only recovery; FedEx synchronous lost-response recovery remains unsupported and blocked. Clearing the enablement switch removes runtime send/reconciliation availability, leaving native booking records/labels intact. Existing current role/site/customer disclosure/consent/restore/native review guards still apply immediately before any write. Enablement cannot establish actual endpoint/company/service acceptance, infrastructure residency, credential custody/rotation or human operating approval.

## Named runtime registrations

Trusted server construction may explicitly register multiple named sandbox carriers for one organization. Each organization/carrier pair must be unique; the same carrier may be registered separately for different organizations. Registration is separate from the customer's named disclosure acceptance. It neither authorizes an undisclosed provider nor grants shipment-site access.

Send and reconciliation resolve the provider from the retained booking through the integration owner after current role/password/organization/site and review-integrity checks. The runtime selects that exact organization/provider pair, regardless of registration order. A missing pair rejects without calling another adapter or changing the booking. HTTP actions continue to accept an empty object only; callers cannot supply a dispatch override. Unknown outcomes retain their original provider and reconciliation never authorizes another purchase.

Registration identity and method handles are captured at construction; mutating the caller's array, binding or method property does not reroute an existing runtime. Adapter methods retain their original receiver. These are trusted code bindings, not an isolation mechanism for untrusted adapters or a credential-lifecycle implementation. Normal startup defaults to no binding, and opt-in UPS/FedEx have original protocol clients with synthetic coverage; the other named protocols remain to be implemented and all actual providers remain to be qualified. See the [local routing receipt](evidence/LOCAL-CARRIER-ROUTING-2026-10-01.md).

A trusted adapter implements `book(intent, beforeWrite)` and read-only `lookup(intent)`. It must call the synchronous guard immediately before its sole write, after preliminary reads, and must not retry writes. The guard repeats current active warehouse/password/site authority, customer acceptance, restore clearance, account credit clearance, exclusive durable claim and unchanged native packed facts. The adapter receives a deeply frozen intent. Returns must identify the exact booking and review hash with canonical reference/tracking and bounded PDF/PNG/GIF bytes; external label URLs and unsupported result fields are rejected. File signature and SHA-256 checks establish byte integrity only, not valid rendering, malware safety, carrier acceptance or physical print readability.

Shared SQLite transactions claim execution and fence abandoned responses. A failed or uncertain operation becomes unknown, including a blocked pre-write operation: operator recovery requires read-only lookup, never a resend. `recoverStale(ageMs, orgId?)` fences stale claims; the default age is two minutes. This is an internal operation, with no automatic carrier worker or public recovery endpoint in this checkpoint. Production timing, process termination, monitoring and recovery procedures require qualification. After an authorized operation, a matching result can be retained if consent or credit changed during I/O; later processing remains subject to current policy. Revoked principal/site/password authority prevents completion and leaves a recoverable unknown outcome.

The trusted startup configuration above supplies a sandbox binding; no browser credential editing, credential lifecycle or actual account qualification is supplied. Do not provision actual credentials or activate requests without authorization and qualification.

The client supports a single ordinary parcel, domestic US or domestic Canada within the configured shipper country. The registered account contact is distinct from the reviewed physical warehouse origin. Positive integer grams/millimeters map to KGS/CM decimal strings. Local conservative caps are 68 kg, 2740 mm longest side and 4000 mm length plus girth; actual service/account/address/parcel eligibility remains unqualified. Customs, cross-border and multiple parcels require further implementation/qualification.

Bounded successful JSON must identify one canonical UPS tracking number and matching shipment number/context, with canonical base64 GIF bytes. Credentials/provider error text are never returned to the operator.

Unknown-outcome lookup authenticates, performs GET tracking by exact reference/account/destination and requires one shipment/parcel with the exact returned reference. Read-only label recovery by that reference must return the same tracking number, matching context and one label, without candidates. It requests no email/URL delivery, purchase or void. The tracking schema defaults to a 14-day search window; absent, expired, ambiguous or inconsistent results remain unknown, never authorize another purchase and require operator/provider investigation. This is a proposed correlation protocol tested against synthetic responses, not proof that a real UPS account/sandbox exposes or echoes these fields. Tracking reads for recovery do not record native delivery observations.

Private GIF downloads retain exact bounded bytes and hash metadata. GIF header/dimensions/trailer checks establish limited structural integrity only; no decoder, rendering, malware or print qualification is claimed.
