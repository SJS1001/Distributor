## Callable contract

`compareOfflineFailedRefundEvidence(input: unknown): OfflineFailedRefundComparison` accepts the exported `OfflineFailedRefundEvidenceInput` profile after hostile-object capture and strict runtime validation. It returns deeply frozen, detached native facts/account binding, exact deterministic request body/hash/idempotency key, the normalized failed result and a domain-separated `inputHash`. It throws one bounded `OFFLINE_REFUND_EVIDENCE` error for unsupported structure or inconsistent facts. Error messages do not echo input data. There is no allowed/qualified flag, import capability, receipt creation, authority assertion or owner mutation.

This is a comparison of **supplied assertions**, including assertions called `coverage`. A caller can fabricate internally consistent input. Matching hashes, account IDs, receipt projections, status strings and singleton membership lists cannot establish authentic issuer/account scope, exhaustive history, external finality, source ordering/fencing, current consent/authority, cash entitlement or safe claim retirement. The future coordinator must obtain exact captured bytes and independently qualified source/provider facts before invoking the owner importer. The importer must re-read real owner rows on its writer transaction and compare the reviewed facts there. No such coordinator or importer is supplied here.

### Supported subset

- One first-observed failed Stripe **test, direct-account** refund. Native effect and native refund are both unknown; effect provider reference/result are null. The external PaymentIntent is declared settled, test mode and exactly matches the original native Stripe payment reference, received amount and currency. Refund object/ID, payment reference, amount, currency and native metadata must agree exactly. Only `failed` is accepted; canceled/pending/requires-action/succeeded are different tasks.
- Native organization/account/invoice/payment/refund projections explicitly distinguish local `payment.id` from external `pi_` identity. All org/account/invoice/refund links, currencies and amounts are compared. Refund amount must be positive and no larger than original payment. CA/CAD and US/USD only; no FX. Invoice total is retained and hashed but is not treated as proof of refundable credit.
- `native.effect` retains every field of the existing `Effect` definition. Other native records are explicit narrow identity/money projections, not complete database rows. `sourceNative` must equal `native` exactly, including effect payload bytes and mutable fields in that projection. Any source-side native settlement/difference is unsupported in this prerequisite. Full invoice/credit/payment/audit source lineage and balance conservation remain owner responsibilities; this helper does not manufacture them from these projections.
- Candidate/source histories must agree exactly. Both must assert `complete-for-subject`, identify the same org/effect/refund, supply the same existing poll with null token/start and enumerate empty provider mappings, observations, callbacks, manual proofs, notices/updates/reads, accounting descendants and generic leases. The helper checks every named collection and refuses omitted, nonempty or extra collections. Null poll token means only that the supplied current row has no token. It does not prove no prior claim existed. Non-null abandoned claims, claim retirement, source-only first-failure application and all preexisting provider/callback histories are explicitly deferred.
- Each history carries exactly two projected Platform receipts, in order: one original `billing.refund.request` and one `stripe.refund`. Org, command, result identity and pending result state are checked. The original request body includes its original reason/reference/local payment identity and must hash to the first receipt; `{refundId}` must hash to the queue receipt. Multiple legitimate queue receipts require a wider profile and are refused. These are caller-supplied receipt projections, not trusted Platform reads; actual complete receipt/audit discovery remains a Platform-owned dependency.
- The non-secret account descriptor requires exact test/direct-account/profile markers and native org/account, runtime binding ID and `acct_` identity. The supplied provider observation must name that same account. This descriptor is not present as authenticated historical account evidence in the old native rows. Its provenance/current association must be supplied independently. Credentials, tokens, Connect/live mode and unknown descriptor keys are rejected.
- Provider membership is an asserted `complete-for-effect` with exactly one matching `re_` ID, equal to the compared refund. No enumeration or provider lookup occurs. The singleton does not prove that another matching refund or later contradictory outcome does not exist.

Inputs are a strict versioned observation profile, **not arbitrary Stripe SDK response objects**. Expanded `payment_intent` objects and additional provider response fields are unsupported. A future private-byte reader/profile must define and qualify how exact provider bytes produce these facts, rejecting ambiguous duplicate JSON keys and accounting for unsupported fields. Do not silently strip unknown fields or treat a caller's normalization as qualification. The helper accepts JavaScript data, not JSON text; it cannot recover duplicate keys already lost by an upstream parser.

## Determinism and original native semantics

The helper imports only `node:crypto`, `node:util` and erased native `RefundIntent`/`Effect` types. No SDK, database, filesystem, clock, transport, callback or mutable owner is imported at runtime.

Native predicates follow the inspected original implementation: [billing-refunds.ts](../src/server/billing-refunds.ts), lines 82–98 and 158–250; [providers.ts](../src/server/providers.ts), lines 82–128 and 175–186. Existing native request and result handling are unchanged. This prerequisite does not perform the native reducer or its balance effects.

The immutable effect payload must equal the exact canonical `RefundIntent` bytes reconstructed from native facts. Whitespace, extra fields, changed casing and alternative key order are refused rather than normalized. The original refund request and queue receipt hashes use SHA-256 of their fixed canonical request shapes. Their known ASCII field names have the same order as native `core.canonical`; independent literal fixture bytes verify the original hashes. Strict text inputs reject surrounding whitespace instead of changing historical values. Previously accepted legacy shapes outside this narrower evidence profile are deferred, not rewritten.

The returned request body is canonical JSON of `{payment_intent, amount, metadata:{effect_id, refund_id}}`; the idempotency key is exactly `distributor:${effect.id}`. This is a deterministic description of the original native request, not a command to send it or proof of transmission/non-transmission. The returned result is exactly `{reference, result:{effectId,refundId,paymentId,amount,currency,status:"failed"}}`.

`inputHash` is SHA-256 of canonical `{purpose:"distributor-offline-failed-refund-comparison-v1",input:capturedInput}`. This **new domain** sorts object keys by code-point order and preserves array order; it does not use locale-sensitive ordering. It binds every accepted input field, including declared coverage, historical receipt identities/times, native effect/error/poll facts and account descriptor. It is not a common envelope or authority binding and must not substitute for one. The full detached return value and all descendants are frozen; caller mutation after comparison cannot affect an earlier result.

## Hostile-object boundary and bounds

Every visited value passes `node:util.types.isProxy` **before** `Array.isArray`, prototype inspection, key/descriptor reflection or property reads. Ordinary and revoked proxies are rejected without invoking their traps, including function proxies and proxies occupying scalar fields. Input objects must have exactly `Object.prototype`; arrays must have exactly `Array.prototype`. A proxied prototype is rejected by identity comparison without reflecting on that prototype. Null/custom/builtin/class prototypes are unsupported.

Capture reads only own data descriptors. It refuses accessors without invoking them, symbol keys, nonenumerable fields, unknown schema keys, sparse/extended arrays, cycles, functions, undefined, bigint, symbols, nonfinite/fractional/unsafe numbers and negative zero. Array `length` is the sole required intrinsic nonenumerable property. Frozen ordinary input is admissible; property writability does not affect content. Detached capture precedes all schema matching, hashing and serialization, so caller `toJSON` is never invoked.

Fixed v1 engineering ceilings: 16 levels, 4,096 visited values, 64 keys per record, 128 array members, 128 characters per key, 8,192 characters per string and 65,536 aggregate string/key characters. Schema limits are tighter: all unsupported history collections are empty, receipts have two elements, membership has one, IDs have at most 128 characters, runtime binding 80, original reason 1,000 and positive money at most 1e12 integer minor units. Exceeding a bound fails; nothing is truncated. ISO receipt/effect timestamps have strict shape and calendar-day validation, but no time freshness/order/authority is inferred. These limits describe parser work, not production/provider/source completeness qualification.
