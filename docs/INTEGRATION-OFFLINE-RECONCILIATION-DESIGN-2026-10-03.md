## Existing mechanics and the confirmed code gap

`billing.refund.request` freezes invoice, native payment, amount, reference and pending state. It bounds pending/unknown reservations against credited cash and bounds all non-rejected refunds against the original payment. `stripe.refund` queues one immutable effect and registers its refund poll. Effect payload is the native `RefundIntent`: `{refundId, invoiceId, paymentId, paymentAmount, amount, currency}`. Here `paymentId` is the external Stripe `pi_` identity, **not** `billing_payments.id`. The native refund row retains that local payment ID. Preserve both identities explicitly. See [billing.ts](../src/server/billing.ts), lines 840–907; [billing-refunds.ts](../src/server/billing-refunds.ts), lines 66–98; [integration.ts](../src/server/integration.ts), lines 551–597, 727–760.

Sending claims `integration_refund_polls`, marks the native refund unknown, marks the effect running and uses provider idempotency key `distributor:${effect.id}`. Before the SDK write it rechecks current identity, hold, poll token, immutable intent and provider choice. A lost result leaves an unknown effect/native refund; an absent lookup remains unknown and never permits a resend. Online completion validates `effectId`, calls the Billing owner, binds the external reference, completes the Integration effect, emits its observation event and retires the poll token. See [integration-refunds.ts](../src/server/integration-refunds.ts), lines 51–247; [providers.ts](../src/server/providers.ts), lines 169–186.

The ordinary `run` API necessarily calls `assertProviderAccess` before claiming and after provider I/O. Supplying a fake adapter containing offline JSON would still require bypassing that gate and would misrepresent a provider read. The missing operation is a **separately authorized, synchronous, transaction-scoped owner completion using already qualified bytes**, with durable offline provenance. It is not another send/lookup endpoint. Leave ordinary gates, `run`, callback handling and existing historical dispositions intact.

Actual claims are disposable rows: `integration_refund_polls(effect_id,org_id,token,started_at,retry_at)`. Normal failure and `recover` clear token/time; `recover` is not evidence of external settlement. Refunds do not use the generic `integration_operation_leases` path. Neither table is an append-only claim ledger or has a revision column. An empty current token cannot prove that no earlier claim existed. `integration.refund.unconfirmed` audit does not retain the old token. See [integration-refunds.ts](../src/server/integration-refunds.ts), lines 24–33, 224–271; [integration-operations.ts](../src/server/integration-operations.ts), lines 12–24; [integration.ts](../src/server/integration.ts), lines 1573–1617.

## Exact v1 admission scope

Recommend task name `integration.stripe-refund-failed.import`, version `1`, with one org, one account, one effect and one native refund. This is a proposed allowlist entry, not an existing exported API.

1. Candidate contains the original `stripe/refund` effect in `unknown`, with null `external_ref` and `result`, and a native refund in `unknown`. Require its immutable request lineage to predate or coincide with the backup cutoff. The post-cutoff outcome belongs to this same intent. Reject pending, running, blocked, rejected and completed effects; a separate future task may address those states.
2. Native invoice, original Stripe payment and credit basis already exist in the candidate and match the source baseline and end. Require native payment/provider reference, original amount/currency, account/org and immutable invoice/credit records to agree. No opening-only or unsupported payment origin, currency conversion, new post-cutoff request, changed money or newly created accounting dependency is imported by this task.
3. There is exactly one poll row in the same org. No generic lease may exist for this refund effect. Require no candidate Billing provider mapping, refund observations, manual refund proof, refund notice/update/read history, refund callbacks or dependent QuickBooks refund intent/allocation for this native refund. Inspect complete sets, not a public history page. Missing or contradictory records refuse.
4. The complete source interval contains no callback lineage or prior differing provider outcome for this subject. Permit either (a) the source never applied this result, or (b) one coherent first native failure completion with the matching observation/notice/event/audit lineage. Case (b) imports the externally qualified outcome through owners; it does not copy source sequence IDs or pretend to replay the source transaction. Any success, requires-action, pending provider observation, additional failure observation, changed binding, related cash/accounting descendant or unrelated subject mutation needs a wider task. Record source observations as immutable provenance references, retaining their order and actual timestamps.
5. Qualified provider evidence supplies exactly one matching refund reference/status `failed` and the original settled test PaymentIntent. It must establish uniqueness of this effect/refund identity in the relevant account and completeness through the independently stopped source end/settled provider horizon. Provider outcome must have occurred in the source interval `(backup cutoff, source end]`; an export created later can attest this only with qualified ordering/time evidence. Timestamp strings alone cannot locate it there.
6. Candidate raw recovery hold and effective provider refusal remain active. Ordinary writers, callbacks, event consumers, provider transport and source writers are fenced by the common phase/operations contract. No release control intent may be outstanding or hidden by a missing current-row projection.

This scope is deliberately partial. A refusal returns a bounded reason and missing evidence categories without changing rows, releasing capacity or claiming the whole restore is reconciled. An unknown or contradictory external result must remain unknown. There is no partial settlement within one task.

## Immutable owner input, review and output

Recommend three internal operations. Names below describe interfaces to implement; none exists at fd763.

`reviewFailedRefundInTransaction(actor, {effectId}, receiptPort)` is read-only, calls `Database.requireTransaction`, refreshes scoped finance authority and returns detached exact native facts, complete ordered lineage counts/hashes, original intent/payload bytes hash, current poll tuple, conservation totals and `ownerStateHash`. It does not return `allowed` or `qualified`, create a claim, resolve external facts, or open its own transaction. Billing supplies its own same-transaction refund lineage projection; Platform supplies the receipt projection. Integration does not read foreign stores directly.

`validateFailedRefundEvidence(review, capturedFacts)` is pure and deterministic. It returns a detached normalized result and comparison hashes or throws. `capturedFacts` is parsed from the same bytes already verified by the private reader; the pure helper cannot certify their origin. It checks the native/provider mappings below and refuses unknown descriptor keys and unsupported outcome variants. Network clients, credentials, clocks, files and caller-provided executable callbacks are not inputs.

`importFailedRefundInTransaction(actor, taskPayload, qualifiedHandle, trustedPorts)` performs the one owner transition under the common writer transaction. `trustedPorts` is root-composed, not deserialized input or a caller-selected SQL/authority proxy. Re-read every native fact and revalidate the pure comparison within that transaction. Input payload has only:

- `version: 1`, `effectId`, `refundId`, `invoiceId`, `nativePaymentId`, `accountId`, `orgId`, `region`, `currency`;
- exact `ownerStateHash`, `intentBytesHash`, `receiptSetHash`, `sourceLineageHash`, `pollStateHash`;
- `providerBindingHash` and the qualified `evidenceSetHash`/`qualificationHash`, with exact evidence references in the common envelope;
- normalized expected `{reference, result:{effectId,refundId,paymentId,amount,currency,status:"failed"}}`, whose hash is bound by the envelope. The owner recomputes it from qualified facts; operator JSON is not the source of truth.

Reject additional fields before canonicalization, including arbitrary target state, amount override, claim replacement, timestamps to backdate native rows, SQL, credentials or `force`. Store original canonical/native payload hashes without normalizing away a difference. Input values may identify rows, never supply replacements for retained facts.

Return only `{receiptId, taskBinding, effectId, refundId, externalReference, effectState:"completed", refundState:"rejected", providerStatus:"failed", observationId, noticeRevision, ownerResultHash, replayed}`. Proposed observation identity access requires a Billing-owned result addition/helper; `observe` currently returns only status. Do not query a foreign “last inserted row” or infer which observation is new. Receipt hash binds exact before/after owner facts, preserved source references, retired claim facts and evidence/authority hashes. Do not return provider reports, secrets or private filesystem paths.

### Receipts, observations and actual claims

Platform command rows retain `(org, actor, name, key, request hash, result, created time)`, not the original request body. Authorization runs before cached-result access. `stripe.refund`'s result is `{id,state}` for the queued effect; it is not a provider-completion receipt. Later refund settlement uses native observations/events/audit, not a new `platform_commands` completion. See [platform.ts](../src/server/platform.ts), lines 81–125, and [integration-refunds.ts](../src/server/integration-refunds.ts), lines 178–217.

Recommend a **new narrow Platform-owned port** returning all matching committed `billing.refund.request` receipts for the native refund and all `stripe.refund` receipts for the effect on the same connection. Include immutable receipt identity/request hash/result/time and relevant complete audit/event lineage. Validate every match; do not assume exactly one queue receipt because separate keys/principals can recover an existing intent. Reject incompatible duplicate identities/results and missing required creation lineage. Never reuse the previous three-command `IntegrationDispositionReceipts` enum for arbitrary command reads; its actual scope is [integration-restore-dispositions.ts](../src/server/integration-restore-dispositions.ts), lines 33–55. The only implemented special Platform receipt reader at fd763 is journal preparation, [platform.ts](../src/server/platform.ts), lines 127–149. A newer independently owned adapter is not verified here.

`stripe.refund` input `{refundId}` is reconstructible. `billing.refund.request` also includes the original reason, which the refund row does not retain. Require a source-bound copy of the exact original request body; recompute its Platform request hash and compare retained IDs/amount/reference and all receipt results. Do not supply a new reason or brute-force a matching body. If that original body is unavailable, this strict first subtype refuses; a future historical admission policy requires explicit separate review. Hash agreement is internal consistency, not evidence of current authority or external settlement.

For Billing lineage include complete provider mappings, observations in sequence order, notices/updates/read acknowledgments, manual proofs, native payment/credit/refund rows and their owner audit/event references. For Integration include effect, refund poll, related generic leases, all matching refund callbacks and dependent accounting intents/allocations. Compare candidate and source baseline/end; explicit empty sets are supported only when exhaustive collection is qualified. First subtype rejects preexisting provider/callback history rather than deleting it. Source first-failure completion, if present, must be exactly coherent with Billing's native observation and notice behavior.

Capture the **actual** candidate poll tuple and the actual source claim evidence before any retirement. A retained token is admissible only for an abandoned lookup on this unknown effect, with independent proof that every actor holding it and every associated in-flight provider operation is settled/fenced. Match exact token hash and row state; never call age-based `recover` to manufacture eligibility. Retire that token atomically with the qualified completion, append its original tuple/hash and the operations proof reference to provenance, and preserve `effect.started_at` and earlier audit rows. If token is already null, record that exact fact and null prior claim; this means no currently retained claim, not that no earlier claim ran. Never fabricate a historical token from a timestamp, UUID, audit ID or provider idempotency key.

Baseline has no durable claim revision or complete token history. Require actual available backup/end tuples and qualified source execution records; identify historical tokens absent from retained data as unavailable, not empty. Missing facts needed to prove settlement are a hard blocker. Recommended common-contract integration: explicitly support a versioned legacy claim representation with exact row-state hash and no invented numeric revision, protected by session CAS and whole-candidate hash. If the common implementation instead requires a durable claim revision, root must supply a migration/qualified admission rule before this task is enabled; a synthetic migrated revision cannot establish historical claim history. This doc does not define or silently change the common envelope contract.

## Required common interfaces and independent authority

Use the [common proposal](RESTORE-OFFLINE-CONTRACT-2026-10-03.md), especially lines 51–140, as a dependency, not a second authority implementation. Required capabilities are:

- A trusted phase/authority assertion on entry and immediately before commit, requiring the native writer transaction, raw active hold plus actual provider refusal, open current reconciliation session and complete release-control lineage. It must reject prior fencing/routing intent until qualified safe stop/settlement and durable supersession establish a new session. A null `current()` release is insufficient.
- A verified private-byte handle binding exactly the named references/bytes/digests to the common evidence set and independently qualified provider/source observations. The same captured bytes must be parsed; no reopen-after-hash race, path supplied by an owner import, descriptor substitution or mutable result object.
- Current finance and security approvals, independent from preparer/executor and each other, plus independently controlled operations authority binding writer fences and provider settlement. Bind current registry revision/hash, revocation state, time/expiry and the complete task envelope. Signatures authenticate the signed statement; they do not establish the truth of provider outcomes or source completeness.
- An explicit trusted mapping from `(org, task)` to an existing native maintenance finance principal, plus current independently qualified association with that principal. Refresh native IAM, org/account access, active status, password/security state and any applicable site scope. External signer IDs must not be cast to `Actor` or used to create/elevate a user.
- Full same-connection pre-task candidate capture, exact task/session CAS, durable receipt finalization and scoped read-only replay, with current external revocation/lease linearized through commit. No remote I/O inside the SQLite transaction. Two timestamp samples alone do not provide that linearization.

These are requirements, not verified callable imports. At fd763 the common document explicitly says its contract is proposed. `captureRestoreCandidate(path)` opens its own snapshot ([restore-review.ts](../src/server/restore-review.ts), lines 102–228); it cannot substitute for the root-owned same-writer capture. `Database.requireTransaction` exists ([database.ts](../src/server/database.ts), lines 221–228), but does not itself grant offline permission. Other lanes' phase, approval and private-reader work must be inspected at the integrated parent before coding a consumer. A branded object or boolean alone is never the common authority boundary.

For provider choice, recommend a conservative v1 admission rule: current `identity.providerAllowed(actor, accountId, "stripe")` must succeed and its returned version must equal the reviewed current choice/acceptance version; the immutable original `effect.residency_version` remains separately bound. Ordinary refund completion intentionally retains an already observed result when consent changes during its authorized I/O ([integration-refunds.ts](../src/server/integration-refunds.ts), lines 168–169). ## Atomic application, conservation and replay

One root coordinator owns `BEGIN IMMEDIATE`. Neither owner review nor import starts another transaction; do not call `Platform.command` inside it. Sequence:

1. Validate common phase, instance/session, current authority and evidence handle. Capture the exact candidate on this writer connection and compare the signed pre-state. Refresh native scoped finance and provider choice. Strictly parse the task and re-read complete owner/receipt projections, source scope and claim tuple; compare their hashes. Require all absence/uniqueness assertions to be complete, not cached list pages.
2. Recompute deterministic refund/PaymentIntent checks from detached qualified facts and the native immutable intent. Recheck no prior provider binding, observations, callbacks or dependent accounting objects and no provider reference reserved by another native refund/effect. The qualified external account binding must match every identity. No projection permits a cross-org write.
3. Integration calls a narrow Billing-owned failed-refund completion in this transaction. Reuse the result validation/reducer behavior of `BillingRefunds.observe`, with explicit current state/history preconditions. Billing appends one observation (`applied=true`), reserves the `re_` identity, changes only this refund to rejected and opens the native failed review notice with its update/audit. Return its exact observation/notice identities to Integration. No Integration SQL touches Billing tables.
4. Integration binds the same external reference, stores the exact canonical native failed result, changes only this effect to completed, clears its current error and retires exactly the reviewed poll token/time. Preserve its original request/reference/payload/residency/creation/start fields. Append the existing `integration.refund.observed` event. Recommend retaining native completion's `retry_at = commit clock + 30000`; failed results are excluded by `due` regardless. Do not schedule work. The distinct offline provenance receipt records the old error/claim facts and distinguishes source outcome time from new local observation time.
5. Assert owner conservation, then recheck common phase/session/IAM/current external authority/evidence pin. Append Integration offline provenance, finalize the common receipt and advance session revision in the same transaction. Any error rolls back all owner rows, observations, notices, events, audits, claim retirement, consumed binding and receipt. No asynchronous callback completes omitted work.

Conservation for this selected first-failure subtype: `paid`, `credited`, `refunded`, invoice `balance`, native payment/credit identities, invoice/stock quantities, accounting allocations and effect count stay identical. The pending/unknown refund reservation sum and this payment's non-rejected refund sum each fall by **exactly this refund amount**, through Billing's native rejected state. All other refunds/reservations stay unchanged; no automatic replacement request or compensation follows. Binding the provider reference prevents this failed outcome being claimed by another refund. A failure is a completed Integration observation, not Integration state `rejected`. The native failed notice stays open for finance review. Formulas are in [billing.ts](../src/server/billing.ts), lines 281–315, 840–907; notice effects are in [billing-refund-alerts.ts](../src/server/billing-refund-alerts.ts), lines 86–128.

For idempotency use the common permanent `(instance,session,owner,org,task,requestId)` scope, consumed binding and owner receipt, with a unique first-failure import per effect/generation. After commit, exact replay is a separately authorized read of the immutable receipt plus surviving native facts. It must not call `observe` again, append another notice/event, refresh poll time or compare the current candidate with the original pre-mutation hash as a new write. Changed input, source/evidence set, provider identity, actor/scope or receipt/owner fact mismatch conflicts. Different keys cannot duplicate settlement. Another task modifying any reviewed owner row/candidate/session invalidates a new write's CAS. Current access and generation rules still govern historical reads; expired approvals grant no further mutation. Crash-before-commit is no change; crash-after-commit returns the one receipt. Do not silently treat missing owner evidence as an idempotent success.

Native events may be appended atomically without running consumers. Existing optional reports must work with reports on/off; the maintenance session must keep ordinary event workers fenced. Receipt stores the complete pre-task candidate hash and normalized owner-result hash, never a recursive full post-state hash containing itself. Final candidate capture and restore release are separate root responsibilities; completing this one task does not reconcile other effects or activate the store.

## Pure validation and qualification work still required

Existing reusable predicates are `StripeAdapter.refundPayment`/`refundResult` at [providers.ts](../src/server/providers.ts), lines 82–128, plus Billing's exact native intent/reference/status checks. They currently sit behind the SDK or inside a mutating owner operation. Extract small pure deterministic helpers in a separately authorized prerequisite; preserve ordinary behavior, transport ordering, stable idempotency and unsupported test-account scope. Add strict offline descriptor parsing separately, without silently narrowing/widening legacy online shapes. A fake secret/SDK client is not a pure validator.

Deterministic matching must include the settled parent PaymentIntent; the raw refund comparison alone lacks independent account/mode evidence. Reject malformed nested objects, unknown offline descriptor fields, secret-bearing descriptors, wrong object/ID/status/metadata/payment, money/currency mismatch and changed native request. Return detached data immune to later caller mutation. Do not export an `allowed`/`qualified` flag. Authentic source/provider provenance, exhaustive membership, trusted time and current permission remain separate qualifications.

Recommend a qualified evidence issuer/profile that produces: authenticated historical/current account descriptor; exact original request linkage; refund and settled payment observations; exhaustive identity search/interval coverage with pagination/completion facts; independently established outcome ordering/finality; and source baseline/end lineage. Require an issuer profile and current authority configured outside both database and manifest, default-disabled. Where Stripe/source facilities cannot supply one of these properties, retain the unknown state and report the specific unsupported property. Neither this repository nor this design establishes that those reports or attestors exist. No provider documentation lookup, account access or external outcome qualification was performed in this assignment.
