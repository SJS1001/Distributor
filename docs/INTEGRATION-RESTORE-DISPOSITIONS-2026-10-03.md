# Historical native integration dispositions — 2026-10-03

This bounded change adds read-only owner projections for an unsent credit application canceled by finance and an unsent checkout superseded by a reviewed replacement. Their `integration_effects` rows remain `blocked`. No row, native receipt, reservation, provider result, recovery hold, transport permission, schema, or public command changes.

Base: `f2d648e755f9d1cbaf26914d13e834906526ccca`. Restore consumer and Platform receipt-source wiring remain root-owned integration work. This change alone does not make restore prepare accept these histories.

## Entry point and ownership

`Integration.restoreDispositionInTransaction(actor, binding, receipts)` requires the caller's existing native database transaction, current staff finance/admin authority, and unrestricted password status. It starts no transaction, opens no second connection, performs no provider lookup and issues no SQL mutation. Calls outside a transaction or from inside an owning SQL callback refuse with `TRANSACTION`; ordinary owning-table restrictions remain enforced.

The exact binding contains `effectId`, SHA256 of the canonical complete current `Effect`, `orgId`, `accountId`, `region`, `currency`, `provider`, and historical `residencyVersion`. The owning organization/customer and billing facts qualify that binding. The effect hash must be obtained from the candidate writer snapshot, not a stale queue page. A changed/missing/malformed row or inconsistent native evidence returns `null` (unresolved); authority failures and unexpected database errors are not successful dispositions.

The result contains the disposition, exact binding, invoice ID, complete evidence SHA256, optional immediate successor ID, and explicit `transportPermission: false` and `externalOutcomeVerified: false`. The evidence hash binds all facts used, including complete command receipt inputs/results, source records, and the currently observed replacement chain or reservation capacity. Returned values are detached data. The evidence digest is a snapshot comparison commitment, not an external signature or provider verification.

Integration reads only its own store and existing Identity/Billing/Checkout interfaces. Credit source qualification reuses the native credit/invoice validator and additionally checks complete original invoice mappings, native credit lines, application identity and reviewed payload. Checkout qualification reuses its owning identity validator.

### Required Platform port

`IntegrationDispositionReceipts.forResultInTransaction(orgId, command, resultId)` is a trusted **Platform-owned** synchronous adapter. Root must implement/wire it using the same `Database` connection and existing candidate writer transaction. It must return every matching committed receipt for the named command/result ID, with organization, actor, command, key, request hash, decoded result and creation timestamp. It must not accept external JSON, use the bounded public audit page, read a different connection, or return a cache. Integration requires exactly one matching receipt, reconstructs its complete native request/result, and verifies its SHA256 and identities.

The commands are only `quickbooks.credit.apply`, `quickbooks.credit.cancel`, and `stripe.checkout.renew`. No generic foreign-table proxy is added. Tests provide this port with a test-only Platform-owned read of actual receipts generated by native APIs. There is no production Platform or restore consumer change in this patch.

## Exact disposition rules

### Canceled unsent credit application

The effect must be the exact QuickBooks credit application in its native cancellation state/message, with null start time, external reference and result. A lease is absent or entirely empty and correctly scoped. Any callback, checkout observation, balance read/observation, refund poll, payment allocation, accounting refund, or checkout lineage attached to this effect refuses qualification, including foreign-org artifacts sharing its ID.

The retained reservation and cancellation must match the same effect, organization, native credit/invoice and exact positive amount. Original invoice and credit effects, full native source facts, mapping references, application reference/date and canonical payload must agree. Reconstructing the original pending effect plus exact reservation/lease must reproduce the retained cancellation review hash. Both original application and cancellation command receipts must match their complete request/result; the cancellation actor, reason, amount and timestamp are bound to that receipt.

The reservation row remains present. Its current disposition is exclusion by this exact native cancellation receipt, the existing native capacity-release rule. Current capacity is included in the evidence hash. A later application can legitimately consume released capacity; it is not settled by projecting the canceled predecessor. Current consent withdrawal does not erase this historical local disposition or grant new permission.

### Superseded unsent checkout

The target must be the exact Stripe checkout in its native unsent replacement state/message with no start, result, external reference, claim or provider artifacts. The complete immutable chain is followed to the original invoice root and forward to its leaf. Missing, cyclic, cross-org/account/provider/invoice, wrong-reference, malformed or ambiguous links refuse qualification. Every native renewal review hash and complete renewal command receipt must agree with the predecessor/successor identities, reviewed replacement amount and reason. Every checkout payload must match its owning invoice identity, number and currency with a valid historical amount. Amounts may differ between generations because native payments can change the balance before renewal.

Native renewal review hashes bind predecessor state/result and successor absence; they do not independently attest an old checkout amount. This projection checks the complete current payload and candidate effect hash, native invoice bounds and exact successor amount in each command receipt. It does not invent a historical provider-account binding or newly verified checkout/payment truth that the native receipt never retained. A previously completed expired/unpaid ancestor can appear in the lineage; its retained original provider identity/result must match the renewal review. This is historical evidence, not a fresh external verification.

**The successor need not be completed for the unsent predecessor to be terminal.** Its existence permanently fences sending the predecessor. The projection grants a disposition only to the requested predecessor. A pending, running, unknown, unrelated blocked or otherwise unresolved successor remains independently unresolved and must still block restore release. The consumer must continue checking every queue row and active claim; it must never treat the returned successor ID or complete chain hash as a terminal disposition of other effects.

Native customer/provider/region/currency bindings are checked. Effects without a retained runtime provider-account binding do not gain one through this projection. External binding, signed restore evidence, independent control repair, active-claim checks, fencing/routing and release authority remain the restore owner's responsibilities.
