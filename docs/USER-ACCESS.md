# User access runbook

Date: 2026-10-01. Local engineering candidate; no product gate is verified. Identity owns principals, grants, security revisions, password hashes and sessions. Warehouse/account validation uses the owning modules. See [implementation](IMPLEMENTATION.md), [contracts](CONTRACTS.md) and the [local receipt](evidence/LOCAL-USER-LIFECYCLE-2026-09-30.md).

## Administrator operations

Customer lookup/list, customer import review/application, customer creation and credit-hold commands now reload the active principal's persisted role/account grants and required-password state. Supplied caller role/account fields cannot expand access. Buyers can read only their current assigned account; an unassigned buyer receives an empty customer list. Creation requires commercial/admin access; credit holds require finance/admin access; imports require admin access. Commands recheck authority before returning saved retries or applying effects. Organization-wide staff customer visibility remains provisional, and this check does not qualify every other module boundary. See the [customer authority receipt](evidence/LOCAL-CUSTOMER-AUTHORITY-2026-10-02.md).

Open Administration → Staff and buyer access. Creating a user requires the administrator's current password; HTTP creation defaults to a required initial password change. Choose a role and permitted warehouses; buyers require an existing customer account. Empty staff site lists currently grant all organization warehouses, so review that selection explicitly. Email addresses are unique across the runtime. No invitation or password-delivery service exists; approved credential handoff remains an operating responsibility.

Edit access changes name/email, role, buyer account, permitted warehouses and active status. Enter the current administrator password and a reason. The displayed security revision must still match; on STALE_USER, refresh and review current values before submitting a new decision. Every successful access edit ends all affected sessions, including edits to name/email. Deactivated users cannot sign in. Reactivation permits a new sign-in but restores no old sessions. An organization must retain at least one active administrator; concurrent demotions/deactivations serialize against that invariant.

Reset password requires current administrator authentication, the target revision, a different 14–256-character initial password and a reason. It ends all target sessions and forces another password change. Revoke sessions similarly requires the current revision/password/reason and ends all sessions existing at that transaction. It does not disable future sign-ins. Both operations advance the target security revision. Actions affecting the acting administrator return to sign-in.

## Personal security

Users with an initial/reset password must change it before opening the workspace or processing finance work. Only session/security, password change, sign-out and own-session termination are available at that stage. Change password requires the current password, a different 14–256-character replacement and matching confirmation in the UI. It clears the forced-change flag and ends all sessions; sign in with the replacement.

Security → End all my sessions → End sessions ends every current session without asking for a password. It cannot increase access. A later sign-in creates a new session. Administrator user lists expose name/email, role/account/sites, active status, security revision, required-change flag and active session count; ordinary users receive only their own security summary. Password hashes, salts, tokens and CSRF values are excluded from these summaries and command/audit payloads.

## Authenticator and recovery codes

Security → Authenticator app supports time-based enrollment for staff and buyers, after any required password change. Enrollment is optional unless their role is selected by the runtime policy. The operator must supply `MFA_ENCRYPTION_KEY` securely: exactly 64 hexadecimal characters representing 32 random bytes, separately stored from the database/backup key and identical across API processes/restarts. Unset means enrollment is unavailable and an already-enrolled user cannot receive a password-only session. An invalid configured value rejects startup. Worker principals remain a separate configured service boundary; interactive MFA does not authenticate workers.

Enter your current password to start a ten-minute setup. Manually add the displayed private base32 key to an authenticator using six digits, 30 seconds and SHA-1. Save the ten individually random 128-bit recovery codes in an approved private location, then acknowledge saving them, enter your current password again and verify the authenticator code. Each recovery code replaces the second factor once; it never replaces the password. Enabling consumes the verification code, advances your security revision and ends every session. Wait for a new authenticator code or use a saved recovery code when signing in again. The accepted authenticator window is the current, previous or next 30-second counter, strictly after the last accepted counter. This prevents same-counter reuse across API processes; a fast device can require waiting for its next counter.

Password-only login for an enrolled principal returns `MFA_REQUIRED` without a session, actor or CSRF token. Submit the same email/password with an authenticator or unused recovery code. Invalid/reused factor codes count toward the shared eight-failure/15-minute throttle; correct password reauthentication during factor setup/removal/replacement does not clear factor failures. A successful complete sign-in clears the counter. Counters are local database abuse controls, not distributed protection or an approved account-lockout policy.

An enabled user sees the enabled status and unused recovery count. For roles with optional MFA, removing the authenticator requires the current password, current security revision and unused authenticator/recovery proof. Removal consumes the proof and commits factor deletion, revision, session revocation and safe audit together. Administrators cannot remove somebody else's factor through these routes; password resets retain the enrolled factor. If every recovery code is lost and the authenticator is unavailable, verified lost-device recovery is still unimplemented. There is no email/helpdesk bypass. Use the recovery-code replacement procedure below while you retain factor access, including for required roles. Use the authenticator replacement procedure below to change devices while retaining an existing factor, including for required roles.

Pending setup material and enrolled secrets use authenticated AES-256-GCM encryption bound to organization/user/purpose. Activated recovery codes retain only user-bound SHA-256 hashes and usage receipts. Enrollment material is returned only through the no-store setup response and held in browser component memory; it is excluded from local/session storage, audit and durable business command results. Expired/replaced/revision-stale setup cannot activate. Startup and each minute in the HTTP process clear at most 100 expired encrypted bundles in deadline order, across organizations, without a runtime key. An authenticated user's expired setup/confirmation request clears their bundle before the denied transaction; password/access/reset/session revision changes clear it atomically with the revision. The latest retry identity remains as one metadata row per user: retrying that same key after expiry or erasure returns `MFA_EXPIRED`; an explicitly new key creates a fresh setup. Activation/removal/restore discard the pending row. See the [cleanup receipt](evidence/LOCAL-MFA-CLEANUP-2026-10-01.md). Encryption keys, recovery codes and setup secrets must never be supplied as command-line arguments or copied to application logs.

The browser clears displayed setup keys, recovery codes and entered password/code at the deadline and refuses an already-expired setup response. Timer execution depends on the browser being scheduled; the server remains authoritative for expiry. Clearing active SQLite values does not securely erase prior pages, WAL files or backups, and JavaScript strings cannot be reliably zeroized. Protect encryption keys and qualify media/backup retention, clock behavior, cleanup backlog and production scheduling separately. Maintenance leaves active factors, recovery-code usage, sessions, grants and native stock/billing facts unchanged.

Setup uses a body retry key scoped to the user/current security revision. An interrupted setup response can retrieve the same encrypted bundle with the same key before expiry. “Start a new setup” replaces pending material. Confirmation/removal intentionally revoke the calling session; an interrupted committed response makes it return 401. Reload/return to sign-in, complete the required factor and inspect the enabled state rather than assuming the operation failed. This differs from the ordinary business command cache: plaintext credentials/setup bundles are never cached there.

Isolated database restore preserves the enrolled secret but discards pending enrollment, invalidates every restored recovery code (a snapshot can resurrect previously used codes) and rejects authenticator counters through the restore's next counter. Wait for a later authenticator counter and sign in using the separately retained runtime key. No automatic factor bypass exists. Snapshot-era factors/grants still need authorized source-cutoff review; changes after backup are not inferred. See [recovery](RECOVERY.md) and the [local MFA receipt](evidence/LOCAL-MFA-2026-10-01.md).

## Replace recovery codes

Open Security → Replace recovery codes while your authenticator is enabled. Enter your current password and select **Prepare replacement codes**. The server checks the current security revision and prepares ten inactive random 128-bit codes for ten minutes. Save them securely. Current unused recovery codes continue working until confirmation. Preparation returns only recovery codes, not the enrolled authenticator secret, and never consumes a factor proof.

A lost preparation response can be retried with the same in-memory key, current password and revision to retrieve the identical encrypted bundle before expiry, including after a server restart. A new key replaces the pending bundle and invalidates its previous confirmation ID. Enrollment and replacement share one pending row per user but use different authenticated encryption purposes; their ciphertext cannot be used across routes. Expiry cleanup and security-revision changes erase pending replacement material using the same bounded maintenance as enrollment. Retrying an erased key returns `MFA_EXPIRED`; prepare with a new key.

To activate, acknowledge **I saved my new recovery codes securely**, enter your current password again and supply an unused code from your existing authenticator or current recovery codes. An inactive new code cannot authorize its own activation. Confirmation atomically consumes that existing proof, replaces all old recovery hashes with ten new unused hashes, discards pending material, advances your security revision, ends every session and records a safe audit. The authenticator secret and enabled status remain intact. Authenticator authorization advances its replay boundary; wait for the next counter before using it again. Single-use recovery proof and concurrent confirmations serialize across API processes. Failed factor proofs count toward the existing authentication throttle.

A successful response returns to sign-in. Use your authenticator or a saved new recovery code. If the confirmation response is interrupted, the operation may already have committed; return to sign-in and check with retained factor access. Do not retry as evidence that replacement failed. Browser cancellation aborts the request and discards late responses, displayed codes, password, proof and acknowledgment. It does not roll back a committed server action. Canceling preparation leaves old codes active, although the inactive server bundle can remain until replacement, expiry or a security change. Canceling confirmation warns that it may have completed. Sign-out/navigation unmounts the panel; expiry clears its contents and already-expired responses are refused. Timer execution depends on browser scheduling; the server decides expiry.

Replacement material uses organization/user/purpose-bound AES-256-GCM in the pending table and is returned through no-store HTTP responses. Codes and entered credentials remain in browser component memory only, outside browser storage, audits and durable business-command results. Activated codes retain only user-bound hashes. Existing key custody, SQLite/WAL/backup erasure, clock, cleanup backlog and memory zeroization limitations still apply. Restore discards pending replacements and invalidates restored recovery codes; replenish using the retained authenticator after its replay hold and a new preparation. This procedure requires existing factor access and does not recover a lost device or an inaccessible encryption key. See the [local replacement receipt](evidence/LOCAL-MFA-RENEWAL-2026-10-01.md). Actual authenticators, independent security review, external security-change notifications and production/operator acceptance remain unqualified.

## Replace authenticator

Open Security → Replace authenticator while an existing authenticator or unused recovery code remains accessible. Enter your current password and select **Prepare new authenticator**. Current password and security revision prepare a new inactive authenticator secret and ten inactive recovery codes for ten minutes. Add the displayed key to your new time-based authenticator (six digits, 30 seconds, SHA-1), then save the new recovery codes securely. Preparation leaves your existing authenticator and unused codes active. A lost preparation response retries the same encrypted bundle with the same in-memory key/current revision, including after server restart.

To activate, enter your current password again, an unused code from the existing authenticator or current recovery codes, and a code from the new authenticator. Acknowledge **I saved my new recovery codes securely**. A new recovery code cannot authorize replacement. Confirmation verifies both factors and atomically replaces the authenticator secret and all recovery hashes, records the new authenticator replay boundary, discards pending material, advances your security revision, ends all sessions and records a safe audit. MFA remains enabled throughout, including for required roles. Rejected proofs and late transaction failures leave the original factor, proof usage, pending bundle, revision and sessions intact; invalid factor proofs count toward the existing shared throttle. Concurrent confirmations serialize across API processes.

Successful confirmation returns to sign-in. Use a saved new recovery code or wait for the new authenticator's next code before signing in: the code used to confirm cannot be reused. If the confirmation response is interrupted, it may already have committed; return to sign-in and establish the outcome using retained new or existing factor access. Browser cancellation discards displayed keys/codes, entered credentials and late responses without undoing a committed server action. Canceling an in-flight confirmation warns that it may have completed. Sign-out/navigation unmounts the panel; expiry clears its contents and already-expired responses are refused. Browser scheduling does not override server expiry.

Enrollment, recovery-code renewal and authenticator replacement share one pending row per user. Preparing a different operation replaces the earlier bundle and confirmation ID. Their authenticated encryption purposes are distinct, so ciphertext cannot be interpreted across confirmation routes. Current identity/organization/password, session/origin/CSRF checks, security revision, bounded expiry cleanup and restore invalidation still apply. New setup material is returned only through no-store responses and kept in browser component memory, outside browser storage, audits and ordinary command-result caches. Existing runtime-key custody, SQLite/WAL/backup erasure, cleanup backlog, clock and JavaScript zeroization limitations remain.

This procedure requires existing factor access. It does not recover a lost device when every recovery code is unavailable, authorize administrator bypass or recover an inaccessible encryption key. Actual authenticators, external security-change notifications, independent security review and production/operator acceptance remain open. See the [local authenticator replacement receipt](evidence/LOCAL-MFA-REPLACEMENT-2026-10-01.md).

## Required role policy

The HTTP runtime accepts `MFA_REQUIRED_ROLES`, for example `admin,finance`. Valid roles are `admin`, `warehouse`, `commercial`, `finance`, `warranty`, `buyer` and `support`. Values must be exact, comma-separated, distinct and without spaces; unknown roles, duplicates and trailing commas reject startup. Unset or empty keeps enrollment optional. Any nonempty policy requires a valid `MFA_ENCRYPTION_KEY` before the database is opened. This implements configuration, not approval of which roles the distributor must require.

Supply the same reviewed policy and encryption key to every API process and restart them together. Configuration is runtime-owned, not stored in the database or encrypted archive; restore does not reconstruct it. Old binaries or an API process with a different policy are not qualified. Changing the policy requires operating review; removing a requirement is not a lost-device recovery procedure.

For a selected role without an enabled authenticator, correct password login creates an enrollment-restricted session. Existing password sessions also become restricted when restarted under the policy; each request derives eligibility from the user's current role and enrolled factor. A required initial password change comes first and ends all sessions. After signing in with the replacement password, the user sees **Set up your authenticator** instead of the workspace. Failed security reads allow retry, reload retains the restriction, and sign-out cancels the pending read. The browser does not request business workspace data during this flow.

At the HTTP boundary, these restricted sessions may use session/security reads, sign-out, setup/confirmation, their password change and ending their own sessions. Every other business API read or write returns `MFA_ENROLLMENT_REQUIRED`. Mutation origin/CSRF checks still apply. Enabled-factor login requires a valid authenticator or unused recovery code before creating any session. Activation ends all prior sessions, so the user signs in again with the factor. Native modules and configured worker principals remain a separate trusted service boundary; this policy does not authenticate workers.

Enabled required-role users see the requirement in Security and have no removal control. The server also rejects removal with `MFA_POLICY` before consuming a recovery code, advancing the revision or ending sessions. Password resets preserve factors, and administrators have no factor-removal bypass. Required-factor replacement and verified lost-device recovery remain open; code replenishment is available while an existing factor is accessible; retain approved recovery material and do not infer an available recovery route from the role policy. See the [local policy receipt](evidence/LOCAL-MFA-POLICY-2026-10-01.md). Local checks do not qualify actual authenticators, deployment policy distribution, production security or administrator recovery.

## Retry and failure behavior

Ordinary business HTTP commands require an authenticated current session, CSRF/origin checks, exact request shape and an idempotency key. Current administrator/password and organization authority are rechecked before cached administrative results. Retry identical pending actions with their original key; changing inputs requires a new reviewed action. A cached revocation reports the original boundary and does not revoke sessions created afterward. Self-revocation/password change invalidates the calling session, so a committed operation with a lost response can make the old session return 401. Return to sign-in; use the replacement password after a password change, then inspect the current state with authorized access.

Successful changes commit credentials/grants, session invalidation, security revision, durable result and audit together. A late-write error rolls them back. Login rereads credentials and active status inside the session/audit transaction after hashing. Failed authentication uses a shared email counter with an atomic SQL increment and 15-minute expiry; eight recorded failures block further attempts until expiry. Counts survive denied business transactions. This is a bounded local throttle, not distributed abuse protection. Sessions expire after eight hours; server authorization reads current principal grants.

## Audit history

After any required password change, current administrators and support staff can open Audit history. It shows organization-wide recorded time, actor ID, action and reference in pages of 20. Actor IDs are stable identifiers, not resolved names/emails. This staff visibility is the existing provisional organization policy; site-specific support restrictions still require operator approval. Buyers and other staff roles cannot read this view. Current active identity, organization, role and password status are rechecked on every read, including the older audit/event compatibility reads.

Load older audit records continues backward beyond the former 200-row limit. A failed request retains loaded records and permits retry. Refresh starts at the newest records; navigation, Refresh and Sign out discard outstanding reads. New activity is excluded from an existing older-page walk until Refresh. Recorded timestamps are evidence fields; ordering follows durable insertion sequence, so tied/backdated timestamps do not reorder a walk. The last-page continuation returns focus to the heading. The new projection omits raw audit details, event payloads and command results. Action/reference metadata can still contain operational identifiers; this is restricted staff information, not a public export.

`GET /api/audit/page` returns `{items,next}` with at most 20 items, each exactly `id`, `actor_id`, `action`, `reference`, `created_at`. `next` is a scoped audit ID or null; supply it as the only optional `after` query parameter. Missing/foreign cursors return the same unavailable-cursor error. The older `/api/audit` retains its authorized raw detail projection and 200-row limit for compatibility; it is no longer the browser audit view.

The additive sequence map and platform-owned clock preserve original audit columns, IDs, bytes and command receipts. Audit insertion and sequence allocation participate in the same transaction, including failures and competing processes. Legacy backfill uses the database's current rowid order; it cannot reconstruct history already lost before upgrade. New sequence identities survive SQLite VACUUM. Back up and stop old binaries before an upgrade; mixed-version writers are not qualified. Startup backfill scans existing history and has no production volume/upgrade qualification. Do not drop/reset the clock or map as a maintenance operation. Audit deletion, retention, export/search/filtering, cryptographic tamper evidence, production locking/load/security/residency and independent operator acceptance remain open. See the [local audit receipt](evidence/LOCAL-AUDIT-PAGES-2026-10-01.md); no task or gate is verified by this interface.
