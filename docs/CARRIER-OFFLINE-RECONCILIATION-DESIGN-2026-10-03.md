## Decision and boundary

Implement **import of an already completed, still-untransmitted Canada Post creation for one retained unknown member of an ordinary-shipment group**. Require every native member to be ordinary, its booking still pending, every claim retired, and the entire group coherently evidenced. One import changes one member to `created`, retains its exact private PDF, and recomputes the existing group aggregate. It leaves every booking pending. This is the smallest useful native settlement: the creation result and transition already exist, and it does not require manifest identity reconstruction, all-booking promotion or custody/finance effects.

This is a recommendation, not an available method. It deliberately does not complete restore eligibility: `restore-activation.ts:346–348` accepts only booked/canceled bookings, transmitted/canceled groups and created members. A group becoming `closed` remains unresolved for activation. A pending sibling remains a separate obligation; neither its cancellation nor its external non-creation follows from this import. Manifest import, absent-at-cutoff records, pending-at-cutoff post-cutoff creates, replacements, individual UPS/FedEx/etc. booking imports, void/refund outcomes and external transmission are later subtypes. Refuse evidence of `transmitted`, mixed transmission or provider-only extra membership here; route it to a future whole-manifest investigation without changing native rows.

The historical canceled-member projection at `carrier-bookings.ts:670–1022` stays read-only and unchanged. Its exact retained cancellation proof is not evidence of provider creation, transmission or source inactivity. In particular, its refusal of missing booking configuration is not relaxed by this proposal.

### Configuration is not a credential and a hash is not an account lookup

`CanadaPostTestClient` validates explicit org/site, test marker, customer number, contract ID, company, pickup/deposit point and service map. Its `configurationHash` is `digest(canonical(binding))`, where binding is the captured config **minus clientId/clientSecret**, including `testApplication` (`canada-post-test.ts:8–25,78–123`). Those excluded credentials may rotate; neither they nor OAuth tokens belong in recovery evidence. The `testApplication:true` marker itself does not prove vendor credential class.

This differs from generic `carrierConfiguration()`'s versioned identity/display-summary hash (`carrier-configuration.ts:7–24`). `captureCarrierConfiguration` checks shape/bounds, not the preimage of its identity (`:42–89`). Canada Post runtime keeps a separate client/hash binding (`carrier-runtime.ts:159–183,303–356`); ordinary configuration lists exclude Canada Post (`:228–246`), and preparation can pass no generic configuration (`:249–272`). Thus the real native history may legitimately have only the group's account configuration hash. The earlier disposition tests' synthetic generic configuration is not a Canada Post account preimage.

For the proposed import require a strictly parsed, authenticated, historical **non-secret Canada Post binding descriptor** with the exact existing binding fields and canonical hash algorithm. Recompute its hash and compare the group; bind its org/site, customerNumber/contractId/company/shippingPoint/service map to independently obtained provider details. Preserve service-array order for hashing. Refuse extras, credentials, unsupported test/production class or missing descriptor. If an intent contains optional configuration, require both configuration fields coherently present, exact group hash, bounded captured shape, Canada Post provider and selected service; do not reinterpret a different generic hash as equivalent. Descriptor evidence can resolve absent display metadata without editing the original intent; it cannot resolve an unrecoverable hash preimage or prove historical account authorization. Missing independent account evidence is a blocker.

## Task-shaped carrier operations

Proposed local-only owner API names, version 1; no HTTP/runtime registration in the first increment:

1. `reviewOfflineCanadaPostCreationInTransaction(authority, {groupId, bookingId, evidenceId})` requires the caller's native transaction and current review admission. Read the verified evidence descriptor, complete bounded carrier state and receipt adapter proofs. Return a frozen review with operation tag `carrier.offline-canada-post-creation.v1`, recovery/source bindings, org/site/group/providerGroup/config IDs, full sorted member commitment, target booking/shipment/customer/lineage hashes, evidence and PDF hashes, claim-retirement references, expected pre-state digest, proposed post-state digest, unresolved-member summary, and `reviewHash=sha256(canonical(versionedBody))`. Return bounded unresolved reasons when otherwise authorized; never return provider secrets or raw addresses in summary. Review has no durable effect.
2. `importOfflineCanadaPostCreationInTransaction(authority, input)` accepts **only** `{version:1, operationId, groupId, bookingId, evidenceId, reviewHash, expectedPreStateHash, approvalRef, reason}` with exact fields. IDs/key maximum 128, reason normalized maximum 160, hashes exactly lowercase 64 hex; approval reference resolves independently verified signed content. Authority context supplies generation/source scope, not a browser-supplied flag. Recompute the review and all authority/evidence dependencies under the same writer lock. On success return `{version:1, operationId, receiptId, generationId, groupId, bookingId, evidenceHash, reviewHash, beforeHash, afterHash, memberState:"created", groupState, unresolved:{pending,unknown}, receiptHash}`. Persist immutable result once. No arbitrary desired state or optional transport/client argument.

An ordinary actor-facing wrapper, if root later exposes one, must retain `identity.currentActor`, warehouse/admin/password and site/account checks (`carrier-bookings.ts:286–353`) before fresh or cached results, in addition to independent recovery authority. A maintenance entry point is not permission to trust a copied actor. Current customer provider consent/credit status must be recorded for subsequent transport eligibility, but must not be falsified or treated as proof that the historical outcome never happened. The recommended evidence-only import does not grant provider access when either policy is currently withdrawn. If owner policy disallows even isolated evidence recording under withdrawal, refuse and record that integration dependency rather than bypass it.

### Required invariant checks before the first write

- Bound SQL membership with at most 101 rows before invoking the existing group reader; require 1–100, exact prepared member set and no extra/inactive/foreign membership. Validate deterministic providerGroupId, group review hash, org/site and preparation proof. Require `group.state=unknown`, no group token/start/observation/manifest bytes/hash, and at least the target unknown. Unknown manifest history is excluded even if someone clears an observation field: receipt/event history must establish member uncertainty and no claimed/confirmed manifest.
- Target must be active `unknown`, token/start/provider_shipment_id/tracking/label_bytes/label_hash all null. Every booking in the group must be pending and have null token/start/reference/tracking/label bytes/type/hash/error. Require latest booking per native target and immediate predecessor matching `intent.previousId`; a predecessor, if present, must be a valid canceled native booking with adequate history. No target replacement IDs in this first subtype. Validate each intent hash, org/shipment identity and current complete packed snapshot, account/site ownership, Canadian origin/destination and one identical origin across the group.
- Every sibling must be claim-free pending, unknown or created. Pending/unknown siblings have no provider artifacts; created siblings have exact valid PDF bytes/hash, provider ID and tracking. Validate all retained created IDs/tracking are unique and their retained outcome history matches. Group aggregate must agree with states. Reject `creating` siblings or any active native booking/member/group claim; no bulk expiry sweep. Complete prepared set and all native state hashes enter the review even though only one member changes.
- Require independent exhaustive external group enumeration under the same Canada Post account/config/providerGroupId, bounded to 100 with no truncated/unresolved pagination. Each external member maps uniquely to one retained native booking/review/customerRequestId. Every already-created native member must appear with identical provider shipment/tracking/label digest and latest `created` status. Target must appear with the matching creation. Other pending/unknown native members may have additional evidenced created outcomes in the same set; keep them pending/unknown until individually approved imports. An omission is recorded as unresolved, never promoted to non-creation. Provider-only extras, ambiguous correlation, duplicate tracking/IDs, transmitted members, a PO or inconsistent details refuse this subtype for the whole group.
- Bind target evidence to org, native customer `account_id` (distinct from carrier customerNumber), warehouse, ordinary shipment/order, booking/review/previousId, complete immutable native snapshot, configuration preimage/hash, providerGroupId and deterministic customerRequestId. Require exact service/code, origin/destination, parcel, pickup/deposit and settlement-account details under that preimage. Different customer accounts may share the group, but each must bind independently; no assumption that the group has a single Distributor customer.
- Call native `validateCanadaPostCreation` (`carrier-bookings.ts:2856–2911`) on the strictly constructed observation. It enforces exact fields, booking/review/config/group correlation, deterministic request ID, provider ID 1–32 safe characters, tracking 11–16 digits, `status=created`, and PDF bytes. `validateCarrierLabel` (`:2744–2774`) checks nonempty bytes at most 1 MiB and file signature. It does not authenticate provider truth, inspect full PDF semantics or bind account/address/parcel details. Do not treat this validator alone as an offline evidence verifier.
- Preserve the existing native duplicate-provider check (`carrier-bookings.ts:1384–1395`) across org/config and all retained groups. Additionally the evidence resolver's account identity must prevent reusing the same provider object across a changed configuration hash for the same actual account; a configuration hash changes with service/shipping settings. Require an atomic account-scoped provider-ID/tracking reservation, described below. Do not make references globally unique across unrelated carrier accounts.

The production protocol already checks those richer details in private async `shipmentDetails` (`canada-post-test.ts:424–517`), after constructing exact request contents in `review` (`:124–245`). Proposed implementation should extract their deterministic expected-detail construction/comparison into pure helpers with regression tests and use them offline with verified response bytes. Keep network fetching and credential validation in the client. Do not instantiate a client with fake secrets or call `lookup` to reuse it. Raw provider export format, authenticity and collection completeness still need a qualified evidence adapter; copying the normalized `CanadaPostShipmentObservation` shape into JSON cannot replace that work. Until that adapter exists, use only an explicit synthetic adapter in tests and declare production import unavailable.

### Claims, atomicity and partial progress

First subtype accepts no live or copied claim. Existing `reviewClaim/releaseClaim` can retire a member's native token after its exact age/review/reason conditions, but only when current common authority admits that operation and establishes old writers/in-flight requests fenced or settled. Age is not fencing. Retain its own command/audit receipt before the import review; bind the release hash and old claim identity into provenance. A crash-retained claim with missing trustworthy lineage remains unresolved. Do not use `recoverStale*` as evidence: those bulk age-based routines do not provide the required independent source proof. If the common phase blocks ordinary release commands, root must supply a narrowly authorized composition of the native release operation; do not bypass `assertCommandAccess` or clear a token from the import.

Apply atomically: revalidate -> reserve exact account/provider references -> append provenance -> update target member to created with exact bytes/hash and null claims -> derive group `closed` if all created, otherwise `unknown` if any unknown, otherwise `creating` -> append native member-created event and a distinct offline-import audit/receipt -> commit. Preserve event payload/version expected by consumers; attach offline provenance through the new receipt/audit instead of silently changing existing event semantics. No booking promotion, stock/cost movement, shipment dispatch, invoice/payment, label purchase/print, manifest send, reporting execution or provider access. Any failure, including audit/event/receipt failure, rolls back the entire import; unlike the asynchronous transport catch path, there is no new external uncertainty to persist after rollback.

Multiple sibling imports are separately approved and serialized. First import invalidates another sibling's pre-state review; re-review/reapprove that sibling against new state with the same immutable external set if still current. Do not mark a subset as whole-group completion. When all are created, native `closed` means awaiting manifest reconciliation, not transmitted or ready to dispatch. A complete external set changing between reviews requires a new evidence identity and authority evaluation; never update old evidence in place.

Late copied completion must fail native token ownership after retirement/import; test both same and independent connections. External completion outside this file is handled by the source fence, not SQLite. Ordinary transport is still held after `group=closed`; offline reconciliation and later activation remain separate authority domains.

### Idempotency and immutable provenance

Carrier stores an append-only versioned receipt keyed by org, recovery generation and operationId, plus uniqueness for generation/group/booking/outcome kind. It binds the exact request fingerprint, target and complete member set, native command/history hashes, source interval/fence evidence, verified external evidence identity/digests, account/configuration commitments, private label digest, before/after hashes, preparer/approver proof references, claim retirement, durable sequence and result hash. Retain full canonical versioned metadata needed for replay; an opaque hash without its referenced immutable evidence is insufficient. PDF bytes stay in private owning storage. No raw secret, credential, signing key or access URL in events/receipts. Evidence retention/access policy is a dependency, not permission to publish private documents.

Same operationId and identical fingerprint returns the original durable receipt after **current** authority, generation, evidence accessibility/integrity and target outcome checks. It must not reapply the original pre-state CAS, since its own commit changed it. Allow later correctly receipted sibling progress without duplicating the target effect; validate the current target against its retained result and the group's legitimate history chain. Same key/different body or new key/contradictory outcome fails conflict; new key/same target cannot create another import. Another actor retrieving an authorized old result must not obtain another effect merely because Platform command keys are actor-scoped. Define a read-only receipt lookup for that case, without a new approval bypass. Missing/corrupt receipt or current target drift must fail closed, not replay the write. Interrupted precommit has no receipt/effect; interrupted postcommit recovers the original receipt. Restoring a backup containing a receipt preserves history but cannot transfer authority into a new generation.

Provider identity reservations are permanent owner records keyed by verified provider account/environment identity and shipment ID, with a separate tracking uniqueness check in that same scope. Reserve on import with a unique constraint and bind booking/group/config/evidence/receipt. Existing native created rows are also checked via their known configuration; conflicting historical hashes whose account identity cannot be established remain a blocker. Do not silently backfill unknown account identities or infer that they are different accounts. Root must choose how that account-resolution coverage is established across retained carrier history; the first slice must refuse when the relevant duplicate-reference search cannot be completed safely.
