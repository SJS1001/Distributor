# Durable restore activation

Engineering implementation based on the published schema-16 checkpoint. The local integration combines restore-release and inventory quantity-error storage in schema 17. Synthetic validation is separate from actual regional recovery qualification. No production adapter, deployment, activation permission or product-gate acceptance is supplied.

## Authority and the application gate

`app.platform.restore` is a filesystem-authorized operator interface. It controls the same `Platform.recoveryHold()` / `assertProviderAccess()` gate used by provider intents, workers, callbacks, credentials and transport. It never deletes `platform_recovery`. A released record alone cannot open the gate: **every runtime process defaults closed** until explicitly configured with a `RestoreActivationAdapter` and a loader for the current separately controlled approver registry. Ordinary platform commands are also held while a release is pending, failed or lacks current authority. Existing isolated rehearsal behavior before preparing a release remains available.

There is no environment-variable bypass, HTTP route or live CLI activation switch. Host composition must configure each application/worker/operator instance deliberately through `app.platform.restore.configure(adapter, loadTrust)`. The adapter must have `enabled: true` and an exact versioned identity; none is installed by the application. Tests supply synthetic adapters only. Restart without configuration, expired approvals, revoked people/roles/keys, changed source or fence identity, lost routing, an expired observation or unknown external effects all close the gate. Short-lived release approvals deliberately bound the initial operating window; this is not an indefinite production authority lease.

## Prepare and independently approve

1. Upgrade only an exact supported schema to a fresh file with the reviewed upgrade procedure. Retain the source, frozen historical hashes and regional/reporting profile. Upgrade changes invalidate old candidate descriptors/signatures. Restore into isolation using the existing encrypted procedure.
2. Reconcile the entire source cutoff and the post-cutoff interval through the intended cutover. Apply any corrections/imports through their owning inventory, billing, identity and integration operations **before** final capture. Retain independently obtained reports as private evidence. This module does not manufacture import facts, write foreign business tables or treat matching report bytes as proof of truth.
3. Stop every candidate writer. Prepare the signed dossier and private evidence manifest described in [restore review](RESTORE-REVIEW.md). `prepare({id, dossier, approvals, manifest})` verifies the candidate, private bytes, current trust, region and exact recovery generation under a SQLite writer lock. It conservatively refuses copied nonterminal effects, callbacks, carrier bookings, grouped shipping, stock journals, authorization/revocation operations and outstanding external-operation claims. A signed report cannot turn copied pending/unknown work into permission to resend it. Unresolved candidates require owning-module reconciliation; if no safe offline operation exists for that record, implementation of that owning operation remains a prerequisite. Direct SQL repair is not this procedure.
4. Retain the returned release `binding`. It binds the release ID, exact dossier (including source cutoff/writer lists/rollback policy), verified evidence-set hash, adapter identity and candidate device/inode. Two distinct current finance/security people, neither the preparer, sign `restoreReleaseApprovalMessage(binding, signerId, role)` with distinct Ed25519 keys. Supply `{signerId, role, dossierHash: binding, signature}` to `approveRelease(id, approvals)`. The signature uses `distributor-restore-activation-v1`; **read-only review signatures cannot authorize activation**. Private signing keys stay in the approved external signing process. Only public registry material and signatures enter this interface.
5. `activate(originalInput)` rechecks exact inputs, private evidence, candidate, both approval domains and current operations observations before committing release. Retain the receipt and journal. Candidate mutation requires a new dossier and approvals; an existing request ID cannot be repurposed.

`platform_restore_releases` retains versioned records, compare-and-swap revisions, input fingerprints, approvals and transition history. A unique partial index permits only one unresolved release across independent SQLite connections. The table's rows are excluded from the candidate **business-data** hash to allow journaling without invalidating the signed business snapshot; its DDL remains bound by the schema hash. Every other application row and the original recovery record remain hashed. The journal is retained in backups. Restoring a released backup supersedes its copied active authorization and preserves its history; the new file/recovery generation cannot inherit a release.

## Operations adapter contract

The adapter is trusted operations code, not a JSON evidence-file interpreter. Its synchronous methods must be bounded and backed by qualified authority. `fence`, `routeCandidate`, `stopCandidate` and `routeSource` receive the exact release ID/binding, candidate/source descriptors, writer lists and evidence-set hash. `observe` supplies a fresh, expiring assertion with that binding, a stable fencing token, source hash/cursor, reconciled evidence set, routing, stopped writer sets and external-effect state (`none`, `observed`, `unknown`). Unknown or malformed outcomes fail closed. It must cover all organizations/providers in the dossier, not just those with a convenient API.

Real implementations must actually establish exclusive authority over old app, worker, CLI, callback and candidate writers, drain or fence in-flight operations, and route to the exact candidate. They must durably deduplicate controls by release identity, reject superseded tokens, and fence delayed controls before reporting `settled: true`. Observation must come from current authoritative operations state or a qualified revocable local authority service; echoing the request, cached report hashes or an unchecked boolean is not proof. No generic network provider is implemented. All configured adapters and current trust services need independent access, residency, credential, failure and timing qualification. A synchronous boundary may require an external operations broker; remote I/O must not be bolted onto business transactions without a separate design review.

SQLite's writer lock protects this candidate file during checks. It cannot fence a different source database, filesystem administrator, network route or an already in-flight provider request. Private single-link files, trusted ancestor directories, controlled filesystem access, reliable storage and qualified infrastructure fencing remain prerequisites. Main-file replacement is detected; protection against a malicious owner of the enclosing filesystem is not claimed.

## Interruption and retained holds

The lifecycle commits `fencing` before calling the fence adapter and `routing` before changing the route. Normal errors persist `held`; process death can leave the intent state. Both keep the real application gate closed. Resume with `activate(originalInput)` after investigating the retained phase. **An uncertain control is not automatically sent again**: resume inspects authoritative settled observations. Failed or expired evidence cannot be overridden by retrying. A delayed operation remains unresolved until the adapter proves settlement/fencing.

Runtime authority loss closes access synchronously. Operator recovery records the next durable hold/stop transition; a permission refusal inside another business transaction is not relied on to commit journal state. A runtime must not cache a successful gate result across later provider dispatch checks.

## Rollback and forward recovery

`rollback(id)` first retains a stopping intent and requests candidate stop. It does not require surviving approval to request a safety stop. Fresh observations must establish both writer sets stopped and all controls settled. Returning to source then requires current independent release approvals, the exact reviewed source cursor/hash, no observed/unknown external effects, and an unchanged full candidate business hash. Any new business write, including security/audit/session changes, conservatively prevents rollback. Source routing runs under the candidate writer lock with the external writer fence still required. A lost response is inspected on restart, never blindly replayed.

New internal effects or external effects retain `forward-held`. No database rewind, money/stock edit, uncertain resend or automatic compensating operation occurs. Investigate and reconcile the new interval with the owning modules. `supersede(id)` permits a fresh release only from a held state with a currently observed isolated route, both writer sets stopped and no unknown external effects. It preserves old history and leaves the recovery hold in place. Capture and obtain fresh review/release signatures for the reconciled candidate. Expired release signatures never authorize source routing; they do not prevent retaining a safety hold and beginning independently approved forward recovery.

## Remaining qualification and integration

The local integration combines platform-owned release storage with inventory-owned quantity corrections and exact older-version upgrade support. Combined historical upgrade and recovery checks are required at that revision. The restore coordinator adds no HTTP/browser activation route or accounting writes.

Actual source freeze/cutoff, warehouse custody, finance reconciliation, current external trust/key custody, confidential storage, live writer fencing/routing, any required owning-module offline imports, continuously refreshed authority, provider readiness and unresolved provider-specific holds must be supplied and qualified before activation. Native lifecycle and synthetic adapter tests do not qualify those systems, RPO/RTO, production volume, power-loss durability or G8. Existing provider/customer/credential checks remain necessary after store release.
