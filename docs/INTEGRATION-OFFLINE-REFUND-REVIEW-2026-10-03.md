## Operation and authority

`integration.reviewOfflineFailedRefundInTransaction(actor, effectId)` requires the caller's existing `Database.transaction` writer transaction. It neither starts nor joins another transaction. `requireTransaction` also prevents entering through a Store SQL callback. The method refreshes current native finance/admin staff authority through the existing `Identity.workerActor`, including organization, active user, no account restriction and password-change checks, then checks current account access. A forged or stale caller role is not accepted as authority.

The selected row must be the caller organization's `stripe/refund` effect, and its exact canonical payload must match `Billing.refunds.intent` reconstructed from the retained native refund/payment/invoice. It checks native org/account/invoice/payment links, organization/account/invoice currency agreement, positive safe-integer refund/payment amounts up to the native 1e12 bound, and refund amount no greater than original payment. **Currency is the organization's configured currency, not inferred from region.** CA/CAD, CA/USD, US/CAD and US/USD are supported when the native records agree.

This is historical read authority only. It works while the recovery hold is active and after current processor consent is withdrawn, retaining the original effect residency version and current account choice as distinct facts. It does not call `providerAllowed`, clear a hold or permit a send, lookup, callback processing, claim retirement, settlement, cash change or follow-on command. Ordinary provider operations keep their existing consent and recovery refusals. External/current maintenance authority, source fencing and signed offline task permission remain separate root responsibilities.

Composition is nine added lines in `integration.ts`; the ordinary state machines are unchanged. The new module invokes only Integration-owned SELECTs, current IAM reads and existing read-only Billing task methods. It has no migrations, writes, provider adapter, clock sampling, HTTP/CLI entry point, supplied evidence, callback port or public SQL parameter.

## Returned facts and limits

The result contains version/scope, org/account/region/currency/effect identities, the original full effect row and native intent, existing Billing `get`/`accountingFact` snapshots, current account, complete selected Integration row sets, explicit blockers and a deterministic `hash`. `IntegrationOfflineFailedRefundReview` exports the deeply readonly inferred result type. Every result is detached with `structuredClone` and recursively frozen; later caller or database changes cannot change an earlier review.

The hash is `digest(canonical({purpose:"distributor-integration-offline-refund-review-v1",facts}))` using native canonical/SHA-256 functions, excluding the hash field itself. Arrays use explicit ID/sequence ordering. All selected columns, original payload/result bytes, terminal rows, exact current claim token/start/retry values and blockers enter the hash. Current native permissions are rechecked on each call rather than encoded as a reusable grant. An unchanged hash does not authenticate source/provider truth or authorize later mutation.

Enumeration deliberately uses a conservative **bounded account scope plus direct subject links**. It reads every Integration effect for the native account, also selecting direct refund/invoice/payment references and the known native nested invoice/payment/refund paths even when a copied row has a changed account column. A selected row from another org/account is a contradiction and is refused without returning that row. This catches the reproduced copied-credit escape. Inclusion of other effects on the same account means unrelated account activity may change the hash or exceed the review bound; callers must obtain a fresh review, never filter the returned set into an authorization decision.

Within that scope it returns:

- `effects`, `polls` and `leases`: all selected effect rows, registered refund polls and generic operation leases, including null or outstanding token/time pairs. Every selected Stripe refund requires its poll. Partial token/time tuples are contradictory. Non-null claims are preserved verbatim and add blockers; age never retires or settles a claim.
- `refundCallbacks`, `checkoutCallbacks` and linked `inbox`: complete selected callback rows, preserving pending through terminal states, attempts, claim timing and references. The review checks native kind, org/effect/reference, event-type/hash shape and duplicate event identities. Checkout/refund aliasing or a checkout inbox row attached to a refund event is refused. A callback raw-event hash is not compared with the checkout inbox's different settlement hash domain.
- `paymentAllocations`, `refundMappings`, `creditApplications` and `cancellations`: retained accounting mappings and receipts, selected by effect and native invoice/payment/refund identities. They must agree with owning effect kinds, snapshot amounts and references. Exact nested predecessor snapshots/references must match completed native QuickBooks predecessors; required mappings cannot be omitted. Terminal canceled applications stay present, with matching amount and blocked effect.
- `renewals`, `checkoutObservations`, `balanceReads` and `balanceObservations`: complete selected checkout and accounting-read history/claims. The review checks renewal predecessor/successor/invoice identity, observation snapshot hashes/subjects and matching balance read/observation identity, sequence and retained result. Nothing is reconstructed from a status string or rewritten to unknown.

Each query first counts at most 65 matching rows and **refuses above 64**, then returns all matches without paging. The entire operation allows at most 512 counted rows, including repeated alias checks, and 2 MiB of accumulated string values plus a separate 2 MiB final canonical result bound. Large payload/result/snapshot/error/reason columns are preflighted before materialization against 64 KiB; all fetched string values also have that bound. JSON objects are parsed with 16-level/4,096-node limits. Limits are fixed v1 engineering bounds, not production-volume qualification; excess throws `OFFLINE_REFUND_REVIEW_LIMIT`. Corrupt or contradictory retained Integration facts throw `OFFLINE_REFUND_REVIEW`. No partial successful page is returned. A `total_changes()` fence additionally checks that successful review did not change the connection.

This review preserves retained facts; its accounting checks do not replace each owning accounting operation's complete settlement/financial validation. Those operations, independent evidence and complete Billing conservation review remain necessary before any future import. The method does not return an allowed/qualified boolean.

## Explicit unavailable prerequisites

Three blockers are always returned at this baseline:

1. `BILLING_COMPLETE_HISTORY_REQUIRED`. Existing `Billing.refunds.get`, `intent` and `accountingFact` are read-only and usable inside the caller transaction. They provide native row identity and any cash reference, but not complete provider observation, notice/update/read, reservation, audit or manual-proof history. `billing_refund_proofs` is **Billing-owned**, not an Integration table. The review never reads it directly. Its existing native accounting fact can expose a retained manual/provider cash reference, which adds an outcome blocker. The separately owned new Billing review API is not present at this exact baseline and is not guessed or simulated.
2. `PLATFORM_RECEIPT_HISTORY_REQUIRED`. No new Platform receipt adapter is accepted or called here. Platform command/audit/event SQL is never read from the Integration store. Complete original request/queue receipt evidence needs the actual Platform-owned prerequisite after root integrates it.
3. `INBOX_UNATTRIBUTED_HISTORY_UNAVAILABLE`. `integration_inbox` has provider/event/hash/time but no org/effect columns. Only rows linked to the reviewed callbacks are attributable locally. Orphan inbox rows are neither assigned to this refund nor exposed across tenants. A refund callback completion does not insert a checkout inbox receipt. Missing/unattributable inbox/callback history cannot be declared absent or complete from this projection; root needs source completeness evidence and wider queue reconciliation.

Additional blockers identify non-first-unknown state, retained provider/manual outcome, refund claims, generic leases, callbacks, accounting, balance or checkout history. Terminal facts can therefore be reviewed without qualifying the first-observed-failure import. The method does not erase inconvenient rows, manufacture cleared claims or classify a copied snapshot as proof of non-transmission. Rows stripped of every retained subject link cannot be attributed by this local operation; independent source interval/account completeness is still required.
