There is no independently generated recovery instance ID, persistent offline session or phase journal yet.
- `Platform.recoveryHold()` can return null when the release coordinator currently permits access, even though the raw hold persists. Neither that method nor raw hold existence proves present infrastructure isolation. The future caller must inspect the raw hold and the effective gate independently.
- `RestoreRelease` starts revision 1 with `{state:"prepared",phase:"prepared",at}`. Every `write`, `hold` and `isolate` increments revision and appends history. `approveRelease()` and exact approval retries append another **prepared/prepared** revision; these are valid and do not imply a control intent.
- Activation records `fencing` before calling `fence`, then `fenced`, `routing` before `routeCandidate`, then `released`. Failure adds `held` at the retained phase. A failed control may already have happened; the intent is sufficient to block offline tasks regardless of outcome.
- Rollback can start directly from **prepared** by recording `stopping` before `stopCandidate`. Therefore `stopping` also records control intent even if no `fencing` entry exists. `returning` precedes source routing; `rolled-back` does not erase earlier intent or prove current isolation.
- Rollback failure/uncertainty uses `forward-held`. Optional `forwardRecoveryRequired:false` distinguishes an interrupted control from a recorded possible effect. Older records omit the flag and remain conservative. No flag proves that an external effect occurred. This evaluator preserves the distinction in the projection but reports a retained forward-recovery marker conservatively whenever history contains `forward-held`.
- `supersede()` requires held/forward-held state and separate adapter checks. `isolate()` may supersede **any** unresolved state, including prepared, without proving external controls settled. Both append retained history. `current()` and the single-unresolved-release index exclude `rolled-back` and `superseded`; neither is a complete-history reader. There is no native literal `failed` state; unknown state names refuse.
- The existing release row hash is `digest(record)` and its JSON identity is compared with row ID/state/revision. This pure projection does not read or authenticate rows or replace those checks. Its lineage hashes are new, explicitly domain-separated proposal hashes and do not alter any native release, candidate or signature fingerprint.

## Exact pure data boundary

`parseOfflineRecoveryGeneration(unknown)` validates, clones and deeply freezes a branded `OfflineRecoveryGeneration`. Its exact fields are `version:1`, `instanceId`, `snapshotHash`, `restoredAt`, `sourceCompletedAt`, `schemaVersion`, `schemaHash`, `region`, `organizations:[{id,currency}]`. The instance ID is a lowercase 64-hex opaque value that **must eventually originate from independent recovery-instance establishment**; this parser neither generates it nor proves uniqueness/independence. Do not derive it from the backup hash or reuse a copied session ID. The other hold fields map exactly to the raw singleton; schema version/hash, region and the complete organization/currency set must come from the same current trusted snapshot. Full candidate logical hashes belong to each task receipt/envelope, not the stable recovery generation.

Hashes are lowercase SHA-256 strings. UTC timestamps must round-trip exactly as `YYYY-MM-DDTHH:mm:ss.sssZ`, with source completion no later than restoration. Parsing these supplied timestamps samples no clock and establishes no freshness. Schema/session/release revisions are positive safe integers; release times are nonnegative safe integer milliseconds. Negative zero, fractional, nonfinite or unsafe integers refuse. IDs are exact nonempty strings up to 160 characters, without leading/trailing whitespace or ASCII control characters. Region is CA/US; organization currency is CAD/USD, independently retained rather than inferred from region. Organization IDs are strictly increasing by JavaScript string comparison, unique, with 1–1,000 entries.

All records require the ordinary object prototype, own enumerable data fields and exact keys. Unknown/missing fields, symbols, accessors, sparse/extended arrays and exotic prototypes refuse. All public entry points revalidate even branded values; a TypeScript cast is no bypass. Normal and revoked Proxies are rejected with `node:util` `types.isProxy` before `Array.isArray`, reflection or property access. Tests assert zero executed caller traps at root and nested record/array boundaries. This is a data parser, not a sandbox against arbitrary code already executing inside the process.

`validateOfflinePhaseState(unknown)` accepts exactly `{version:1,generation,releases,sessions}` and returns a cloned, deeply frozen, data-only branded state. Each session is `{id,revision,phase,previousSessionHash,lineageHash,history}`. There are at most 1,000 sessions, with at most 10,000 aggregate session history entries. Each history step is exactly `{revision,kind,phase,receipt,reason,previousHash,releaseHistoryHash,lineageHash}`. Steps start at revision 1 and are contiguous; head revision equals history length and head phase/hash equals the last step. Every prior session must be terminal before another starts. Session IDs never repeat. No closed or invalidated session can reopen.

A receipt is exactly `{owner,orgId,taskName,requestId,binding,payloadHash,beforeCandidateHash,resultHash}`. Its organization must belong to the generation. The permanent request identity `(owner,orgId,taskName,requestId)` cannot repeat within the same session, and a consumed binding cannot repeat anywhere in the generation's retained sessions. Names describe a receipt; they are not a dispatch allowlist or executable operation. A receipt supplied to this model is **unqualified proposed data**, not proof of a native owner commit. A future owner/coordinator must establish its exact native effect and current authority in the writer transaction. No receipt-update or deletion transition exists.

`OfflineReleaseHistory` is a strict, typed projection of the existing release: `{id,binding,revision,state,phase,at,history,forwardRecoveryRequired?}`. The trusted future caller must load **every** retained release, authenticate full records/row hashes and construct that projection; passing full records with extra properties or only `current()` is unsupported. Projection arrays permit up to 1,000 releases and 10,000 aggregate history entries, reject duplicate IDs and competing unresolved heads, and are canonically sorted by ID. Every history starts prepared, has one entry per revision, preserves nondecreasing time, follows native possible phase edges and matches its current head. Terminal histories cannot continue. Malformed, future or unsupported forms refuse rather than infer safety.

`classifyOfflineReleaseHistory(unknown)` returns only a barrier classification and count: `no-recorded-release`, `prepared-release-retained` or `control-intent-retained`, plus `not-established` or `forward-recovery-marker`. These labels are not infrastructure observations. Prepared-only superseded history remains a barrier. Control intent remains present through later holds, rollback and supersession, regardless of a later prepared release. No `verified`, `authorized`, `canImport` or permit output exists.

## Evaluator and lineage

`offlinePhaseExpectation(state)` returns `{generationHash,stateHash,session:null|{id,revision,lineageHash}}`. It is a pure expected-data anchor, not proof of currentness. `evaluateOfflinePhaseTransition(current,expected,transition,observedReleaseHistory)` requires exact equality with that anchor, validates complete observed releases, and refuses removal, binding replacement, revision regression, rewritten prefixes, same-revision changes or loss of an already-true forward-recovery marker. Its only successful output is `{status:"static-phase-proposal",next,expectation,releases}`, deeply frozen and detached from all caller-owned data.

| Transition                     | Static precondition and resulting proposal                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `{kind:"isolate",sessionId}`   | No active session, new never-used ID, no retained release. Append a proposed `isolated` session at revision 1, linked to the preceding terminal session. This does **not** create a native hold or establish external isolation.                                                                                                                                            |
| `{kind:"open"}`                | Latest session isolated, no retained release; propose open. Current approvals/authority/fencing remain separate obligations.                                                                                                                                                                                                                                                |
| `{kind:"record-task",receipt}` | Latest session open, no retained release; append the immutable receipt and advance revision/hash. No owner mutation occurs.                                                                                                                                                                                                                                                 |
| `{kind:"drain"}`               | Latest session open, no retained release; propose draining. There is no in-flight claim model in this increment, so new or finishing task receipts in draining are unsupported.                                                                                                                                                                                             |
| `{kind:"close"}`               | Latest session draining, no retained release; propose closed. This does not qualify reconciliation, release a hold or activate a provider gate.                                                                                                                                                                                                                             |
| `{kind:"invalidate",reason}`   | Latest session isolated/open/draining; propose terminal invalidation while retaining all receipts and newly observed release history. Reasons: generation-changed, authority-lost, evidence-changed, operator-abandoned, release-observed. A reason records a claim, not proof. A mismatched generation anchor still refuses; this transition cannot rotate the generation. |

Any retained release blocks every transition except invalidation. There is deliberately no prepared-release retirement, qualified-stop boolean, supersession override or post-intent resumption path. Independent qualified stop/settlement, fresh review and a separate recovery procedure must be implemented before such work. Once invalidation binds a nonempty release journal, this evaluator supplies no further transition to rewrite or advance that journal; retain it for separate recovery/history handling.

Hashes use SHA-256 of the repository `canonical()` encoding with these exact purpose domains:

- Generation: `distributor-restore-offline-generation-v1`, binding the complete generation object.
- Session seed: `distributor-restore-offline-session-v1`, binding generation hash, session ID and preceding terminal session lineage hash (null for the first).
- Release projection: `distributor-restore-offline-releases-v1`, binding the complete sorted projection array.
- Step: `distributor-restore-offline-step-v1`, binding generation hash, session ID and every step field except its own lineage hash. `previousHash` is the preceding step or session seed. `releaseHistoryHash` is the empty journal for ordinary transitions; final invalidation binds the exact observed journal. An earlier release-free invalidation stays bound to an empty journal if a later distinct session is created.
- State: `distributor-restore-offline-state-v1`, binding the complete validated generation, sessions/receipts and retained releases. This prevents an old release or session disappearing from an expected checkpoint even when it is no longer active.

These are integrity chains, not authentication. A fully rewritten/rehashed self-consistent snapshot is syntactically valid; it cannot match an independently trusted current expectation. If **all** inputs are stale or forged consistently, a pure function cannot discover the real database state. The future coordinator must compare actual same-writer state, external generation establishment, release-row history and signed envelope anchors, and atomically CAS the exact expected revision/state. Unit tests explicitly preserve this distinction.
