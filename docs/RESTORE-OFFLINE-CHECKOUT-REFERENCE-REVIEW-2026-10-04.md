## Resource and byte boundaries

All complete fixed sets pass numeric SQL count/type/field/row/aggregate-byte/NUL preflight **before retained text or JSON materializes in JavaScript**. Billing caps each set at 256 rows, total 1,024; Integration caps each at 64, total 512. Both cap fields at 64 KiB, rows at 128 KiB and conservative escaped-JSON aggregate budget at 2 MiB (six times retained UTF-8 bytes plus fixed key overhead). A cap is a refusal, never truncation. No `PRAGMA`, reflection-driven column discovery, JSON virtual table, foreign SQL or caller-selected predicate is used.

Bounded same-row hexadecimal byte witnesses and fatal UTF-8 decoding reject lossy SQLite TEXT materialization before hashing. NUL and type/unsafe-integer violations refuse in SQL. Integration additionally scans string/bracket boundaries before JSON parsing, with depth 16, at most 4,096 conservative nodes/document and 16,384 across documents. Iterative post-parse validation precedes recursive canonicalization and rejects unsupported primitive/property forms, unsafe integers/-0, reserved/oversized keys, unpaired surrogates and NUL escapes. Exact canonical equality rejects duplicate keys, BOM, whitespace/alternative serialization and trailing material. There are no user object/parser callbacks in that path.

The same-writer whole-store candidate operation remains the existing Database owner's implementation. Its other-module resource policy and external filesystem/source/provider/current-authority fences through COMMIT remain root infrastructure responsibilities. These fixed bounds qualify only the stated owner sets and current call; they are not a whole-product latency, store-size or authenticity claim.
